# fxDevKit 架构设计

> 文档定位：**用户视角**的概念与设计决策。
>
> 配套 `docs/详细设计.md`（实现视角、数据流、API、调用链）。
>
> 本文件回答三个问题：**fxDevKit 是什么**、**你用它要做什么**、**它跟别的东西怎么配合**。
>
> 不涉及具体函数签名与代码实现细节——那部分在《详细设计》。

---

## 0. 一句话定位

**fxDevKit 对人的增强：人有目标，需要能力去达成，能力就是插件。**

你手里有一个百宝箱，三种方式打开它：

| 入口 | 怎么触发 | 当前状态 |
|---|---|---|
| **自动触发** | 动作发生时自动执行（`git commit` → 插件改写 message） | 已实现 |
| **主动触发** | 你敲命令（`fxdevkit status`、`fxdevkit <plugin> <cmd>`） | 已实现 |
| **对话触发** | 你说一句话，AI 去调 skill 和 MCP | 演进方向 |

它不替你决策、不接管你的代码，只让你**看得更清、打得更准**——动作照旧做，增强在背后发生。

**用它的这个人当下在做研发，所以装的插件以研发类为主——这是需求的当下状态，不是产品的边界。** 内核不含任何领域语义，所以将来换目标（HR、设计）只需换插件，内核一行不动（详见 §2.1）。

## 1. 用户视角：你只需要知道这三件事

> 这一节是文档核心。从用户出发，不讲系统内部路径。

### 1.1 三种入口（你怎么打开这个百宝箱）

| 入口 | 你怎么用 | 系统做了什么 | 状态 |
|---|---|---|---|
| **自动触发** | 你照常 `git commit` / `git push` | 动作发生时自动跑插件，不用你多敲一个字 | 已实现 |
| **主动触发** | 你敲 `fxdevkit ...` | 调起内核命令或插件命令 | 已实现 |
| **对话触发** | 你在飞书 @ 机器人说一句话 | AI 理解意图，去调插件提供的 skill 和 MCP | 演进方向 |

**自动触发**最省心：装一次全局 hooks，之后所有仓库的提交都会被增强，你什么都不用做。

**主动触发**最显式：查状态、跑插件能力，就敲命令。

**对话触发**是演进方向：入口不再局限于终端——飞书群里看到告警，直接 @ 机器人说"基于这个 reqId 查一下线上日志，为什么报这个错"，AI 去编排调用。**具体能力仍由插件提供，内核不实现任何一个 skill。**

> 前两种今天就能用；第三种契约位置留着，等真实需求出现再落地，不会返工。

### 1.2 配合授权（系统需要你给什么）

系统正常运行需要你授权以下内容，**都是一次性的**：

| 授权 | 你做什么 | 为什么要 |
|---|---|---|
| **git hooks 授权** | 跑一次 `fxdevkit install` | 让所有仓库的 git hook 都先经过系统，并**默认全部增强** |
| **排除某个目录（可选）** | 在该目录跑 `fxdevkit disable` | 默认全部增强，只有显式排除的目录才例外 |
| **插件权限** | 插件 manifest 里声明 `permissions` | 没声明的能力 → 给空实现（不报错） |
| **作用域（可选）** | 在 `~/.fxdevkit/config.yaml` 配 `plugins.<id>.projects` | 不配 = 全局生效；配了 = 只在指定目录生效 |

**核心语义：装一次全局 hooks，所有目录默认增强**。收窄范围有两条路——`exclude` 黑名单（`fxdevkit disable`，写在用户配置里）与插件的 `projects` 白名单；**黑名单优先**。系统不会自动改你的 git config、自动装插件。

### 1.3 看反馈（你想知道什么，就用什么命令）

| 你想知道 | 用什么命令 |
|---|---|
| 系统是否健康 | `fxdevkit doctor` |
| 当前仓库状态 | `fxdevkit status` |
| 谁被执行了 / 结果如何 | `fxdevkit logs` |
| 某个插件的日志 | `fxdevkit logs --plugin <id>` |
| 事件统计 | `fxdevkit report` |

设计取舍：正常 commit 时**终端完全静默**——不打扰你的提交节奏。日志默认只落盘（`~/.fxdevkit/logs/`），要看就 `fxdevkit logs` 拉出来。

## 2. 系统由什么构成（四层）

四个层级，**单向依赖**，每层只有一种职责：

| 层 | 是什么 | 用户视角对应 |
|---|---|---|
| **CLI** | 子命令解析、输出格式化 | 你敲 `fxdevkit ...` 时的翻译层 |
| **Core** | 调度器 + 10 个通用模块 | 系统的"大脑"——知道找插件、装载、派发 |
| **Plugin** | 一个或多个独立 npm 包 | 具体做事的人，每个都能独立替换 |
| **SDK** | Core 与 Plugin 之间的协议 | "插件长什么样、ctx 里有什么"的契约 |

```
+---------------------------------------------------+
|  你敲的命令                                         |
|    git commit / fxdevkit run / fxdevkit status     |
+---------------------------------------------------+
                        |
                        v
+---------------------------------------------------+
|  CLI 层  (packages/cli)                            |
|    子命令解析 + 帮你格式化输出                      |
+---------------------------------------------------+
                        |
                        v
+---------------------------------------------------+
|  Core 层  (packages/core)                          |
|    调度器（找插件 / 装插件 / 授权 / 派发）         |
|    10 个通用模块（git / 配置 / 日志 / 事件 ...）   |
+---------------------------------------------------+
                |               |
                v               v
+---------------------------------------------------+
|  Plugin 层  (packages/plugin-*)                    |
|    每个插件 = 一个独立 npm 包                       |
|    唯一依赖：@fxdevkit/sdk                          |
+---------------------------------------------------+
                        ^
                        | (契约)
+---------------------------------------------------+
|  SDK 层  (packages/sdk)                             |
|    定义插件长什么样、ctx 里有什么                   |
+---------------------------------------------------+
```

### 2.1 不可违反的约束

| 约束 | 含义 |
|---|---|
| **单向依赖** | CLI → Core；Plugin → SDK；Plugin 不依赖 Core 或 CLI |
| **插件独立** | 插件之间不互相调用、不互相 require |
| **Core 不代笔** | Core 只编排，不替插件写文件/落事件——动手的事给插件 |
| **通用下沉、专属留插件** | 多个插件都要用的能力下沉到 Core；只有某个插件用的写在插件内，不受限制 |
| **内核不含领域语义** | 内核里不出现任何具体领域的概念——这是目标可切换的前提 |

关于后两条：

**通用的边界靠审核识别，不靠预判。** 先让插件自己实现，用得多了、多个插件都要了，再上升到内核。审核看三件事：复用度（几个插件在用）、副作用面（碰不碰网络 / 凭证 / 系统目录）、独立性（这个插件还能不能单独演进）。

**内核不含领域语义不是洁癖。** 它直接决定产品能不能换目标：

```
内核无领域语义  +  领域语义全在插件
        ↓
换目标 = 换插件，内核一行不动
```

**已知欠债**：当前内核里 git 语义偏重（`git.ts`、`HOOK_NAMES`、`findRepoRoot`）。这是当下形态自然形成的，**现在不急着还**，但从此刻起不再新增——往内核加任何东西之前，先过一遍上面的三项审核。

## 3. 核心概念（你需要理解的 4 个）

### 3.1 插件（Plugin）

**插件是系统的可变部分**。所有具体能力（commit 检查、依赖审计、接口同步……）都由插件承担。

- 插件 = 一个独立 npm 包，名字带 `plugin-*` 或 `fxdevkit-plugin-*`
- 插件在两处声明自己：`package.json` 的 `fxdevkit` 字段（manifest）+ 代码里的 `definePlugin({...})`
- 两处 `id` 必须一致，否则系统丢弃
- 插件不依赖 core，不依赖其他插件
- 删一个插件 = `rm -rf packages/plugin-<name>`，无需卸载命令

### 3.2 内核（Core）

**内核是系统的不变部分**。它做四件事：

1. **发现** —— 从 node_modules 找插件
2. **装载** —— 加载插件代码
3. **授权** —— 检查权限，构造 ctx（上下文）
4. **派发** —— 在 git hook 时刻或 fxdevkit 命令时刻调插件

除此之外内核不做事。它不写你的文件、不替你 commit、不替你发请求。

### 3.3 契约（SDK）

**SDK 是内核和插件之间的唯一协议**。插件作者只需 `import { definePlugin } from '@fxdevkit/sdk'`，剩下的事（ctx 构造、派发）由内核做。

SDK 只声明、不动手：不发请求、不读文件、不 spawn 子进程。

### 3.4 授权（Permissions）

插件要做什么事，必须先在 manifest 里声明 `permissions`。**未声明的能力 = 空实现**：

| 声明 | 拿到什么 | 没声明拿到什么 |
|---|---|---|
| `fs:repo` | 仓库内读写 | 空 |
| `fs:read` | 只读 | 空 |
| `events:write` | `ctx.emit` 可用 | 静默函数 |
| `net:server` | `ctx.server` 可联网 | 拒绝客户端 |
| `git:write` | git 写操作（amend/rebase） | 空 |

**这是安全边界的核心**：插件拿不到没声明的东西，**也不会因为没声明而崩**。它优雅降级。

## 4. 工作机制：三种入口各自怎么走

> 用真实场景把工作机制讲清楚。**这是用户视角**，内部代码位置见《详细设计》。

### 4.1 自动触发：一次 `git commit` 发生了什么

**你敲的**：

```bash
git commit -m "fix: 修复XX"
```

**背后发生的**：

1. git 看 `core.hooksPath`，发现指向 `~/.fxdevkit/hooks/`
2. git 跑 `~/.fxdevkit/hooks/commit-msg <msg-file>`——这只是个 shim，实质就一行：把控制权交给 fxdevkit
3. fxdevkit 调内核，内核做四件事：
   - **发现**——扫 node_modules，找出声明了 `commit-msg` 的插件
   - **装载**——校验身份（manifest 与代码的 id 一致），合并配置（源码默认 + 用户覆盖）
   - **派发**——把 message 和插件自己的配置交给插件
   - **兜底**——插件出错、超时、配置非法，一律跳过
4. 插件检查 message、加 `AI ` 前缀，写回文件，返回 0
5. git 看到 exit 0，用改写后的 message 完成 commit

**你看到什么**：终端完全静默，但 message 已经被改写了。全程有日志落到 `~/.fxdevkit/logs/`。

**关键的兜底**：任何一步出问题都不会卡住你的提交——插件抛异常、超时（默认 1000ms）、甚至 fxdevkit 被卸载导致入口失效，git 都照常提交。

### 4.2 主动触发：你敲命令发生了什么

**你敲的**：

```bash
fxdevkit status
fxdevkit logs --plugin plugin-commit-rules --last 10
fxdevkit plugin-commit-rules check --sha HEAD
```

**背后发生的**：

1. CLI 解析命令。内置命令（`status` / `doctor` / `logs` / `config`……）直接由内核处理
2. 不是内置命令时，按**插件 name** 路由——`fxdevkit plugin-commit-rules check` 里的 `plugin-commit-rules` 是插件短名，CLI 源码里不出现任何插件 id
3. 内核装载插件，执行它声明的命令

**跟自动触发的差异**：这条路径可以输出内容，也可以返回非零退出码（比如 `check` 发现不合规则返回 1，给 CI 用）。

### 4.3 对话触发：演进方向

**设想的用法**：飞书群里看到告警，@ 机器人说"基于这个 reqId 查一下线上日志，为什么报这个错"。

**背后会发生什么**：

1. IM 收到消息，转给 AI 大脑
2. AI 理解意图，从内核收集到的 skill 里找到能干这事的（查日志）
3. 通过插件提供的 skill 或 MCP 调用外部系统
4. 结果回到群里

**当前状态**：不实现，但契约位置留着——插件清单里 `hooks` / `commands` / `skills` 三者并列，将来加 `skills` 不用改内核。内核只负责收集 skill，**不实现任何一个**。

### 4.4 三条路径的共同点

无论哪条入口，内核做的都是同一件事：

```
发现 → 装载 → 授权 → 派发 → 兜底
```

变的只是**谁触发**和**结果怎么回**：

| 入口 | 谁触发 | 结果怎么回 |
|---|---|---|
| 自动触发 | git 动作 | 写回文件或放行，正常情况终端静默 |
| 主动触发 | 你敲命令 | 输出到终端，可返回退出码 |
| 对话触发 | AI 大脑 | 结果回到对话里 |

## 5. 什么时候用 fxDevKit、什么时候不用

### 5.1 适合用

- 团队对 commit message 格式有规范，想强制落地
- 想自动记录"这次提交触发了什么"
- 多个项目共享同一套研发动作约束
- 想要在不动业务代码的前提下，给流程加钩子

### 5.2 不适合用

- 想要取代 git/IDE 的（这是增强器，不是替代品）
- 想在仓库里塞业务代码的（fxDevKit 不接管业务代码）
- 想要一个"装上就能自动配好一切"的工具（系统不自动安装、不自动启用）

### 5.3 跟 husky/lefthook 怎么配合

- **husky/lefthook**：项目级 hook 管理（在 `<repo>/.git/hooks/` 或 `.husky/`）
- **fxDevKit**：跨项目的 hook 入口（全局 `~/.fxdevkit/hooks/`）+ 插件派发

**fxDevKit 内部**保留了仓库自有 hook（`runRepoOwnHook`），所以 husky/lefthook 装了照样能跑——它们是项目级 hook，fxDevKit 是分发层。两者**共存而非替代**。

## 6. 核心设计决策（已拍板）

| 决策 | 取舍 | 文档位置 |
|---|---|---|
| 插件之间不互相调用 | 强隔离；通过事件订阅做间接联动 | §2.1 / §3.4 |
| Core 不替插件动手 | 编排权清晰；插件自主性高 | §2.1 |
| 通用下沉、专属留插件 | 通用边界靠审核识别，不靠预判 | §2.1 |
| 内核不含领域语义 | 目标可切换的前提；git 语义欠债暂不还但不再新增 | §2.1 |
| 全局 hooks 装一次，所有仓库默认增强 | 目录收窄用 exclude（黑名单）或插件 projects（白名单） | §1.2 |
| 配置只有「源码默认 + 用户覆盖」两层 | 工程目录零侵入，仓库根目录不写任何文件 | 详细设计 §8.1 |
| 事件订阅只在命令路径生效 | hook 路径订阅会拖慢提交 | 详细设计 §8.2 |
| 用户自己 `npm i` 装插件 | Core 不做安装器；简化 core 复杂度 | 详细设计 §9.3 |
| 默认 mock server | 默认不联网，必须显式关掉才连真服务 | 详细设计 §2.2⑨ |

## 7. 边界与待决议

### 7.1 已拍板的边界

- 插件之间不互相调用（铁律）
- Core 不替插件写文件/落事件（铁律）
- 事件订阅只在命令路径生效
- 全局 hooks 装一次，所有目录默认增强（`fxdevkit disable` 可单独排除某个目录）
- 用户自己 `npm i` 装插件

### 7.2 仍待讨论

| 待决项 | 关键问题 | 状态 |
|---|---|---|
| `subscriptions` 是否会松化"插件互相隔离"铁律？ | 订阅是经 Core 事件总线的"间接通道"，跟直接 import 是不是一回事？ | 未决 |
| 是否需要 `requires` 字段声明插件依赖？ | 强声明 vs 弱约定？ | 未决，倾向不做 |
| 第二个插件的形态 | 哪种能力最有说服力证明架构？ | **暂缓**——先把内核和第一个插件做稳 |
| 远程仓库名 `FocusDevKit` 与产品名 `fxDevKit` 不一致 | 该改哪个？ | 未决 |
| 产品名带 `Dev`，与「对人增强」的张力 | 人换目标后名字还贴不贴切？ | 留给将来，现在不动 |
