# dev-kit 技术落地方案（V2）

> 配套文档：`00-产品定义.md`（定位与流程映射）。本文只讲 how。
> 已确认：Node + TS / npm 包插件 / Server 先本地 mock / commit-rules 打样 / 声明式权限 + 内核强制。

---

## 一、架构总览

CLI 与 Server 双端。真实凭据只存在于 Server，CLI 仅持有可吊销的 device token。

```
本地 CLI 运行时                       Server 管控面
├─ 命令入口                            ├─ 插件注册表
├─ 插件运行时（本地缓存/离线可执行）    ├─ 鉴权与凭据保管
├─ 钩子托管（hooksPath/自动重装）       ├─ Monitor（注册数·使用数·计量）
└─ 本地会话（device token）             └─ 配置下发
        └────────── HTTPS ────────────────┘
```

当前阶段 Server 为**本地 mock**，接口契约与真实实现一致，未来切 HTTP 只需替换一个工厂函数。

## 二、仓库结构

```
devkit/                            npm workspaces（Node 22 自带 npm，不引入 pnpm）
├── packages/
│   ├── sdk/                       @devkit/sdk       插件协议类型 + definePlugin
│   ├── core/                      @devkit/core      微内核
│   ├── cli/                       @devkit/cli       bin: devkit
│   └── plugin-commit-rules/       @devkit/plugin-commit-rules
└── docs/
```

依赖方向严格单向：`plugin → sdk`、`core → sdk`、`cli → core + sdk`。core 不依赖 cli，插件之间互不可见。

## 三、插件协议（packages/sdk）

插件通过 `package.json` 的 `devkit` 字段声明清单：

```json
{
  "devkit": {
    "id": "commit-rules",
    "apiVersion": 1,
    "hooks": ["commit-msg"],
    "commands": ["check"],
    "permissions": ["events:write", "git:read", "fs:repo", "proc:exec"]
  }
}
```

内核启动时校验 `apiVersion`，不匹配则跳过并告警——这是未来内核升级不炸插件的唯一保险。

插件实现侧：

```ts
export default definePlugin<Config>({
  id: 'commit-rules',
  priority: 100,
  defaultConfig: DEFAULT_CONFIG,
  validateConfig(raw) { /* 归一化 + 校验，非法即抛 */ },
  hooks: { 'commit-msg': async (ctx) => 'modify' | 'accept' | 'reject' | void },
  commands: { check: { describe, handler } },
})
```

`ctx` 由内核注入：`config` / `logger` / `git` / `args` / `messageFile` / `emit` / `server` / `permissions`。

## 四、内核实现（packages/core）

| 文件 | 职责 |
|---|---|
| `paths.ts` | 全局目录约定，可用 `DEVKIT_HOME` 覆盖 |
| `config.ts` | 分层配置：插件默认值 → 全局 → 仓库 → 环境变量。**数组整体替换，对象递归合并** |
| `git.ts` | 仓库/分支探测、merge/rebase/cherry-pick 状态、**amend 状态传递** |
| `plugins.ts` | 插件发现、加载、权限集合 |
| `permissions.ts`（并入 plugins） | 权限判定 |
| `events.ts` | 事件 JSONL 落盘，`~/.devkit/events/YYYY-MM.jsonl` |
| `server.ts` | Server 客户端：mock 实现 / HTTP 实现 / 拒绝实现 |
| `hooks.ts` | dispatcher 脚本生成、`core.hooksPath` 安装与卸载 |
| `kernel.ts` | 派发编排、超时、熔断 |

### 4.1 插件发现

扫描以下目录，按 id 去重：

1. `<repo>/node_modules/@devkit`
2. `<repo>/node_modules`
3. `~/.devkit/plugins`
4. `~/.devkit/node_modules/@devkit`
5. `DEVKIT_PLUGIN_PATHS` 指定目录
6. CLI 自身安装位置的 `node_modules`（`npm i -g` 场景）

匹配包名前缀 `@devkit/plugin-*` 或 `devkit-plugin-*`。

### 4.2 amend 状态传递（容易做错的点）

`commit-msg` hook 拿不到命令行参数，**无法自行判断 `--amend`**；只有 `prepare-commit-msg` 能拿到 `source` 与 `commit sha`。

因此：

- `prepare-commit-msg`：`args[1] === 'commit' && args[2]` → 判定为 amend，写入 `~/.devkit/cache/commit-state.json`（key 为仓库根目录，5 分钟 TTL）
- `commit-msg`：消费并清除该状态

漏掉这一步，amend 出去的提交会被重复注入前缀。

### 4.3 熔断与离线降级

三层保险，任何一层都不允许阻断 git 操作：

**第一层 — dispatcher 脚本的退出码约定**

```sh
#!/bin/sh
"<node>" "<cli>" hook commit-msg "$@"
code=$?
[ "$code" -eq 1 ] && exit 1    # 只有插件业务性 reject 才阻断
exit 0                          # 其余一律放行
```

**第二层 — 内核编排**

- 单个插件硬超时（默认 1000ms，`DEVKIT_HOOK_TIMEOUT_MS` 可调），超时即跳过
- 插件加载失败 / 配置非法 / 执行抛异常 → 记录 warn 后 `continue`
- 整个 `dispatchHook` 外层 try/catch，任何意外返回 0

**第三层 — CLI 入口**

`hook` 子命令下的未捕获异常强制 `exit 0`。

> 离线可用性是第一约束。插件本地缓存、本地执行、异步上报；所有网络调用带超时且失败静默。
> 这条守不住，工具会在第一次 Server 抖动时被卸载。

### 4.4 权限模型（声明式 + 内核强制）

插件在 manifest 声明权限，内核在**构造 ctx 时按权限裁剪能力**，而非事后检查：

| 权限 | 未授予时的行为 |
|---|---|
| `events:write` | `emit` 替换为静默空实现 |
| `net:server` | `server` 替换为拒绝客户端，记录一次越权尝试并返回空值 |
| `fs:repo` / `git:read` / `proc:exec` | 供后续内核代理层裁剪，插件不得绕过 |

关键点：插件永远拿不到长期凭据，只能通过 `server.exchangeCredential(scope)` 向内核换取短期、最小权限的令牌。

### 4.5 Server 客户端

```ts
createServerClient({ url, mock, timeoutMs })
```

- mock 或无 url → 本地实现，读写 `~/.devkit/mock-server/`（usage.jsonl / credentials.json / config.json）
- 有 url → HTTP 实现，`POST /v1/usage`、`/v1/credentials/exchange`、`/v1/config`

三种实现接口完全一致，切换无需改动插件。

## 五、commit-rules 插件

### 5.1 commit-msg 执行流程

```
读取提交信息文件
  ↓
[守卫] merge / rebase / cherry-pick / amend → 放行（emit commit.guarded）
  ↓
[守卫] 分支不在 scope 内 → 放行
  ↓
[规则匹配] 有 pattern 的规则按顺序短路
  ├─ 命中 skip   → 放行（emit commit.passed）
  ├─ 命中注入型  → 改写（emit commit.rewritten）
  └─ 无命中      → 应用兜底规则（无 pattern 的那条）
  ↓
写回文件（dryRun 时不写）
```

### 5.2 幂等性交叉校验

兜底规则注入的前缀，必须能被某条 skip 规则匹配，否则同一条 message 被二次处理会变成 `AI AI xxx`。

`validateConfig` 阶段做静态探测：用兜底规则的 value 拼一条探针 message，检查是否有 skip 规则能匹配；不能则直接抛错，并给出建议 pattern：

```
规则「default」注入的「AI」无法被任何 skip 规则匹配，会导致重复注入。
建议新增 { name: 'default-guard', pattern: '^AI', action: 'skip' }
```

### 5.3 默认配置

```yaml
plugins:
  commit-rules:
    rules:
      - name: ai-explicit
        pattern: '^(AI|ai)[:\s]'
        action: skip
      - name: no-ai
        pattern: '^(chore|docs|merge|revert)[:\s]'
        action: skip
      - name: default
        action: prefix
        value: 'AI '
    branches: ['*']
    dryRun: false
```

`action` 支持 `skip` / `prefix` / `suffix` / `template`（template 支持 `{message}` 占位）。

### 5.4 CI 侧强制

`devkit check [--sha <sha>]` 校验提交信息，不修改任何内容，不合规返回 1。

本地 hook 能被 `git commit --no-verify` 绕过，真正的强制要落在 CI。命令与事件结构现在已就位，推广时零改造。

## 六、命令

```bash
devkit install                  安装 git hooks（core.hooksPath 托管）
devkit uninstall                卸载
devkit plugin list|add|remove   插件管理（add 安装到 ~/.devkit）
devkit config show|validate     查看生效配置 / 校验插件配置
devkit check [--sha]            提交信息校验
devkit report                   本地事件统计
```

`post-checkout` 时若检测到 `core.hooksPath` 不再指向 devkit，自动重装——解决 clone 后 hook 丢失的问题。
