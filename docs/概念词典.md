# fxDevKit 概念词典

> 把所有术语集中解释，每个术语配**真实代码片段**与**代码位置**。
> 读完你应该知道每个词是什么、在哪用、跟其他词什么关系。
>
> 阅读路径：从 §0 总图建立全景 → §1 用户视角最常碰的 5 个概念 → §2-3 实现视角再深入。

## §0. 术语全景

```
                              你敲的命令
                                  │
                                  ▼
                          ┌───────────────┐
                          │   dispatcher  │  ← 一个 shim 脚本，转发到 fxdevkit hook
                          └───────┬───────┘
                                  ▼
                          ┌───────────────┐
                          │   kernel      │  ← 内核调度器（dispatchHook / runPluginCommand）
                          └───────┬───────┘
                                  ▼
                          ┌───────────────┐
                          │  discoverPlugins│  ← 从 4 个目录扫 manifest
                          └───────┬───────┘
                                  ▼
                          ┌───────────────┐
                          │   loadPlugin  │  ← 动态 import + 三层授权
                          └───────┬───────┘
                                  ▼
                          ┌───────────────┐
                          │   构造 ctx    │  ← 按 permissions 注入字段
                          └───────┬───────┘
                                  ▼
                          ┌───────────────┐
                          │  plugin.hook  │  ← 你写的代码（真正干活）
                          │  /commands    │
                          └───────┬───────┘
                                  ▼
                          accept/modify/reject
```

下面每个术语，都会在上面这张图里出现一次以上。

## §1. 用户视角最常碰的 5 个概念

### 1.1 插件（Plugin）

**是什么**：一个独立的 npm 包（`packages/plugin-<name>/`），只依赖 `@fxdevkit/sdk`，不依赖 Core、不依赖其他插件。

**真实代码**（`packages/plugin-commit-rules/package.json`）：

```jsonc
{
  "name": "@fxdevkit/plugin-commit-rules",
  "version": "0.1.0",
  "main": "dist/index.js",
  "fxdevkit": {              // ← manifest，下一节讲
    "id": "commit-rules",
    "name": "commit",
    "apiVersion": 1,
    "hooks": ["commit-msg"],
    "commands": ["check"],
    "permissions": ["fs:repo", "events:write"]
  }
}
```

**配什么位置**：`packages/sdk/src/index.ts`（manifest 类型定义）+ `packages/core/src/plugins.ts`（发现/装载）

---

### 1.2 清单（Manifest）

**是什么**：插件的「自我描述」，写在 `package.json` 的 `fxdevkit` 字段里。内核**先读 manifest 判断「这是个什么插件」**，再决定要不要 `import` 它的代码。

**所有 manifest 字段**（来源：`packages/sdk/src/index.ts:28-41`）：

```ts
export interface PluginManifest {
  id: string                   // 唯一标识；与代码侧 definition.id 必须一致
  name?: string                // 命令行短名（fxdevkit <name> <cmd>）；不写就取 id
  apiVersion: number           // 协议版本，不匹配则跳过
  hooks?: HookName[]           // 订阅哪些 git hook
  commands?: string[]          // 对外暴露哪些子命令
  permissions?: Permission[]   // 声明能力；未声明的拿不到（给空实现）
}
```

**两处声明必须一致**：manifest 的 `id` ↔ 代码里的 `definePlugin({id: 'commit-rules'})`。
不一致会被 `loadPlugin` 拒绝装载（详细设计 §7「三层授权」）。

---

### 1.3 hooks / commands / subscriptions

这是 manifest 里**三个声明「做什么」的字段**，彼此互不重叠：

| 字段 | 声明什么 | 触发时机 | 代码侧对应 |
|---|---|---|---|
| `hooks: ['commit-msg', ...]` | 订阅哪些 git 动作 | git 触发 hook 时 | `definition.hooks[<name>]` |
| `commands: ['check', ...]` | 暴露哪些 CLI 子命令 | 用户敲 `fxdevkit <name> <cmd>` | `definition.commands[<cmd>]` |
| `subscriptions: [...]` | 订阅别人发的事件 | **仅命令路径**激活 | `definition.subscriptions[<pattern>]` |

**真实代码**（`packages/plugin-commit-rules/src/index.ts`）：

```ts
export default definePlugin({
  id: 'commit-rules',
  hooks: {
    'commit-msg': async (ctx) => { /* git commit 时被调 */ }
  },
  commands: {
    check: {
      describe: '校验提交信息',
      handler: async (argv, ctx) => { /* fxdevkit commit check 时被调 */ }
    }
  }
})
```

**与权限的关系**：所有 hooks / commands 都在「被调度」时收到构造好的 ctx。
ctx 里的字段（`emit` / `server` / `config` / `logger` / `git`）按 manifest 的 `permissions` 授予。

---

### 1.4 权限（Permissions）

**是什么**：插件 manifest 里声明的「能力清单」。**未声明的能力 = 空实现，插件优雅降级，不报错**。

**所有权限**（来源：`packages/sdk/src/index.ts:19-26`）：

```ts
export type Permission =
  | 'fs:repo'      // 仓库内文件读写（commit-msg 改写提交信息就靠它）
  | 'fs:global'    // 读 ~/.fxdevkit/*
  | 'git:read'     // 读 git 信息（ctx.git 无条件注入，不需要此权限）
  | 'git:write'    // git 写操作（amend / rebase）
  | 'events:write' // ctx.emit 可用；未声明时是空函数
  | 'net:server'   // ctx.server 可用；未声明时是拒绝客户端
  | 'proc:exec'    // spawn 子进程
```

**为什么这么设计**：让插件代码**不必做权限判断**——直接用 `ctx.emit(...)`，没声明就是空操作；直接 `ctx.server.reportUsage(...)`，没声明就是被拒绝。代码始终保持线性。

**配什么位置**：`packages/core/src/kernel.ts` 里 ctx 构造的判断逻辑（约 130-180 行，按权限逐个 if 注入）。

---

### 1.5 内核（Core）

**是什么**：系统的不变部分。它做四件事，**仅此四件**：

| 阶段 | 函数 | 做什么 |
|---|---|---|
| 发现 | `discoverPlugins` | 从 4 个目录扫插件 |
| 装载 | `loadPlugin` | 动态 `import()` + 校验身份 |
| 授权 | `permissionSet` | 按 manifest 构造权限集合 |
| 派发 | `dispatchHook` / `runPluginCommand` | 调插件 handler |

**Core 不做的事**（硬约束）：

- ❌ 不写你的文件（写文件是插件 + `fs:repo` 的事）
- ❌ 不替你 commit / 不替你发请求
- ❌ 不替你给别的插件传数据

**配什么位置**：
- 调度器：`packages/core/src/kernel.ts`（`dispatchHook` + `runPluginCommand`）
- 通用模块：`packages/core/src/{paths,git,config,events,logger,scope,hooks,server}.ts`
- 包导出：`packages/core/src/index.ts`

## §2. 实现视角的核心概念

### 2.1 dispatcher

**是什么**：装全局 hooks 时，core 在 `~/.fxdevkit/hooks/<hook-name>` 下生成的 shim 脚本。
每个 hook 一个文件，**只是个一行 wrapper**，负责把 git 转给 fxdevkit CLI：

```sh
# ~/.fxdevkit/hooks/commit-msg
exec "<cli-entry>" hook commit-msg "$@"
```

**真实代码**（`packages/core/src/hooks.ts` 的 `installGlobalHooks`）—— 它会写出一堆这样的 shim。

**为什么这么设计**：git 的 `core.hooksPath` 只能指向**目录**（不能指向具体程序）。
所以要让 fxdevkit 拦截所有 hook，必须自己做一个目录、里面放 shim。
而 shim 的存在让 git 把每个 hook 调用交给 fxdevkit 处理。

---

### 2.2 ctx（HookContext / CommandContext）

**是什么**：调度器在调用插件 handler 之前构造的对象，包含「插件做事需要的一切」。
插件不构造 ctx，只**接收 ctx**。

**两个 ctx**（来源：`packages/sdk/src/index.ts:74-98`）：

```ts
// git hook 触发时
interface HookContext<C> {
  pluginId: string
  config: C                            // 已合并 + 校验过的本插件配置
  logger: Logger                       // 走 plugin 通道的 logger
  git: GitContext                      // { root, branch, isMerge, isRebase, ... }
  args: string[]                       // git 传给 hook 的原始参数
  messageFile?: string                 // commit-msg 时是提交信息文件路径
  emit: (type, payload) => void        // 无 events:write 时是空函数
  server: ServerClient                 // 无 net:server 时是拒绝客户端
  permissions: ReadonlySet<Permission>
}

// 用户敲 fxdevkit <name> <cmd> 时
interface CommandContext<C> extends HookContext<C> {
  command: string                      // 当前子命令名
  // 注：没有 args 和 messageFile（不是 git 触发的）
}
```

**字段注入原则**（`packages/core/src/kernel.ts`）：

```ts
const ctx = {
  // 无条件注入（不需要权限）
  pluginId, config, logger, git, permissions,
  args, messageFile,

  // 按权限注入
  emit: permissions.has('events:write')
    ? createEmitter(pluginId, ...)
    : createSilentEmitter(),
  server: permissions.has('net:server')
    ? createServerClient(...)
    : createDeniedServer(pluginId, logger),
}
```

---

### 2.3 HandlerResult — accept / modify / reject

**是什么**：插件 handler 的返回值，**告诉内核该怎么处理这次动作**。

```ts
type HookOutcome = 'accept' | 'reject' | 'modify' | void
```

| 返回值 | 含义 | 内核行为 |
|---|---|---|
| `accept`（或不返回） | 放行 | 继续 |
| `modify` | 我已改写（如改了 messageFile） | 标记该插件为 modify，不再二次处理 |
| `reject` | 阻断 | 整次 hook / 命令返回非 0，git 会中止 commit |

**真实代码**（`packages/core/src/kernel.ts` 的结果收集）：

```ts
let rejected = false
for (const plugin of candidates) {
  const result = await plugin.hooks[hookName](ctx)
  if (result === 'reject') rejected = true
}
return rejected ? 1 : 0
```

**关键**：**一个 reject 阻断整次**（即使其他插件说 accept）。多插件场景下，任一 reject = 整次阻断。

---

### 2.4 配置（Config）

**是什么**：插件的可调参数。结构 = 用户覆盖 + 插件默认值的合并。

**三层配置**（来源：`packages/core/src/config.ts`）：

```
全局   ~/.fxdevkit/config.yaml
项目   <repo>/.fxdevkit.yaml
环境   FXDEVKIT_* 环境变量
```

合并规则：**项目级覆盖全局级**（`{...global, ...project}`）。

**真实代码**（`packages/plugin-commit-rules/src/index.ts`）：

```ts
export default definePlugin({
  id: 'commit-rules',
  defaultConfig: {
    rules: [{ action: 'prefix', value: 'AI ' }],
    branches: ['*'],
    dryRun: false,
  },
  validateConfig(raw) {
    // 归一化 + 校验；非法时 throw（被捕获后跳过该插件）
    return { rules: raw.rules ?? [], ... }
  },
})
```

**配什么位置**：
- 加载：`packages/core/src/config.ts` 的 `loadConfig(repoRoot)`
- 抽取：`pluginConfig(config, pluginId)` —— 给某个插件看自己那一块
- 合并/校验：`packages/sdk/src/index.ts` 的 `validateConfig`（插件自己实现）

---

### 2.5 作用域（Scope / projects）

**是什么**：某个插件「只在哪些目录下生效」。**插件无感**，内核判定。

**声明位置**（`~/.fxdevkit/config.yaml`）：

```yaml
plugins:
  api-sync:
    enabled: true
    projects:                # 不写 = 全局生效
      - D:/products/order-service
```

**判定逻辑**（`packages/core/src/scope.ts`）：

```ts
function isPluginInScope(config, pluginId, repoRoot) {
  const projects = config.plugins?.[pluginId]?.projects
  if (!projects || projects.length === 0) return true   // 不配 = 全局
  return projects.some(p =>
    repoRoot.toLowerCase().startsWith(p.toLowerCase())   // 前缀匹配
  )
}
```

**关键设计**：判定由内核做，**插件不需要知道**。插件代码不需要写「我是不是该跑」这类判断。

---

### 2.6 日志（Logger）— 双通道

**是什么**：所有调度与执行都有日志，**分两条通道落盘**，用户可用 `fxdevkit logs` 拉出来。

| 通道 | 谁写的 | 内容 |
|---|---|---|
| `core` | 内核调度器 | 「派发 hook」「候选 N 个」「[id] 执行」「[id] 完成」 |
| `plugin` | 插件（通过 `ctx.logger`） | 插件自己的输出 |

**打印策略**：

| 级别 | hook 路径 | 命令路径 | 落盘 |
|---|---|---|---|
| `error` | stderr | stderr | ✅ |
| `warn` | stderr | stderr | ✅ |
| `info` | 只落盘 | stderr + 落盘 | ✅ |
| `debug` | 只落盘（需 `FXDEVKIT_DEBUG=1`） | 同上 | ✅ |

**为什么默认静默**：避免每次 commit 刷屏。想实时看就 `FXDEVKIT_DEBUG=1`。

**配什么位置**：`packages/core/src/logger.ts`

---

### 2.7 事件（Event / emit）

**是什么**：插件发出去的结构化记录，落盘到 `~/.fxdevkit/events/YYYY-MM.jsonl`。

**真实代码**：

```ts
// 插件侧
ctx.emit('commit-rules.rewritten', { branch: ctx.git.branch })
```

**订阅**（仅命令路径激活）：

```ts
// 另一个插件的 manifest
{
  subscriptions: [
    {
      pattern: 'commit-rules.*',
      handler: (event, ctx) => { /* 事件发生时被调 */ }
    }
  ]
}
```

**关键约束**：**hook 路径不触发订阅**——避免拖慢提交。这是「间接插件间通道」的边界，详细设计 §8.2。

**配什么位置**：`packages/core/src/events.ts`（落盘 + 订阅分发）

---

### 2.8 Server / Mock

**是什么**：插件访问外部平台（Apifox、AI、需求平台）的客户端。

**三态**：

| 状态 | 谁注入 | 何时 |
|---|---|---|
| **mock** | `createMockServer()` | 默认。系统不联网，纯本地 |
| **真实** | `createServerClient(config)` | 设置了 `FXDEVKIT_SERVER_URL` |
| **拒绝** | `createDeniedServer(pluginId, logger)` | 插件没声明 `net:server` 时 |

**默认 mock**——系统绝不主动连真服务。`fxdevkit doctor` 显示当前状态。

**配什么位置**：`packages/core/src/server.ts`

---

### 2.9 默认全局生效 vs 仓库显式停用

**是什么**：装全局 hooks 之后，所有仓库**默认都被增强**，唯一例外是显式停用的仓库。

**存储**：

| 项 | 存哪 | 命令 |
|---|---|---|
| 全局 hooks 是否装 | `git config --global core.hooksPath` | `fxdevkit install --global` |
| 本仓库是否停用 | `git config fxdevkit.enabled` | `fxdevkit uninstall` |

**关键设计变化**：早期版本「逐仓库安装 hooks」让新仓库不生效——这正是用户痛点。
现在**装一次全局 hooks 就好**，新仓库自动接入；要排除的才用 `uninstall`。

## §3. 数据流术语（按一次 git commit 串起来）

按一次 `git commit -m "..."` 的执行顺序，相关术语依次是：

| # | 术语 | 这一步做什么 |
|---|---|---|
| 1 | **dispatcher** | shim 把 git 转给 `fxdevkit hook commit-msg` |
| 2 | **dispatchHook** | 内核调度入口 |
| 3 | **discoverPlugins** | 扫 4 个目录，找声明了 `commit-msg` 的插件 |
| 4 | **selectPlugins** | 按 hook 名 + scope 过滤候选 |
| 5 | **loadPlugin** | 动态 `import()` + 三层授权 |
| 6 | **permissionSet** | 从 manifest.permissions 构造权限集合 |
| 7 | **ctx** | 按权限逐个字段注入 |
| 8 | **hooks[hookName]** | 插件 handler 被调 |
| 9 | **modify / accept / reject** | handler 返回值 |
| 10 | **logger** | core 与 plugin 各写一条日志 |
| 11 | **exit code** | 任一 reject → 返回 1，git 中止 commit |

**配什么位置**：`packages/core/src/kernel.ts` 的 `dispatchHook`，约 60-180 行。

## §5. 术语别名/同义

| 别名 | 正式名 |
|---|---|
| dispatcher / dispatcher 脚本 / shim | 全局 hooks 安装产物 |
| manifest | `package.json` 的 `fxdevkit` 字段 |
| id | 插件内部唯一标识 |
| name | 插件命令行短名 |
| 派发 | 内核调度器调插件 handler |
| 兜底 | 出错时的安全路径（不阻断 git） |
| 调度器 | kernel.ts 的 `dispatchHook` / `runPluginCommand` |
| 通用模块 | core 里被 ctx 注入的能力 |
| 双通道日志 | core 通道 + plugin 通道 |

## §6. 容易混淆的概念

| 容易混 | 区别 |
|---|---|
| **id** vs **name** | id 是配置键与事件记录用；name 是命令行短名。两者可以不同（多数情况相同） |
| **HookContext** vs **CommandContext** | 前者是 git 触发；后者是用户触发。CommandContext 多一个 `command` 字段，少 `args/messageFile` |
| **hooks** vs **subscriptions** | hooks 监听 git 动作；subscriptions 监听别插件发出的事件。后者只在命令路径激活 |
| **permissions** vs **scope** | permissions 决定插件能用什么能力；scope 决定插件在哪些目录生效。两者完全正交 |
| **mock server** vs **拒绝 server** | mock 是"假装有 server、纯本地"；拒绝是"插件没权限访问、调用就记录告警" |
| **enabled: false** vs **fxdevkit.enabled = false** | 前者是插件级（config.yaml）；后者是仓库级（git config） |

## §7. 新人最常问的 5 个问题

**Q1：为什么 manifest 和代码里都要写一遍 id？**
A：manifest 让内核判断「这是个什么插件」；代码让内核判断「这是不是那个插件」。两者必须一致，否则装载失败（身份不符）。

**Q2：插件能不能用 Node fs 读写文件？**
A：能。权限 `fs:repo` 只是一种声明（让别的工具知道你打算读写仓库文件），并不是强制隔离。**真正的隔离需要沙箱**——目前没有，假设所有插件可信。

**Q3：插件抛错会怎样？**
A：内核 catch 该错误，记日志，跳过该插件。**其他插件照常执行**；如果有别的插件 reject，整次 hook 仍然阻断。

**Q4：日志那么多条，怎么只看某个插件的？**
A：`fxdevkit logs --plugin <id>`。

**Q5：怎么知道一个插件在哪些仓库生效？**
A：`fxdevkit status` 显示每个插件的 scope 命中状态；不在命中内的会标「未生效」并给出原因。
