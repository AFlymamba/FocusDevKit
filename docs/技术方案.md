## 一、架构总览

```
fxdevkit（CLI）                       命令层
├─ 参数解析
├─ 调用内核能力
└─ 结果格式化
        │
        ▼
@fxdevkit/core                        内核
├─ 调度器
│   ├─ 发现      扫描目录、读清单、去重、取版本最新、apiVersion 识别
│   ├─ 装载      加载模块、校验身份、合并配置、授予能力
│   ├─ 派发      动作触发时按声明路由到插件
│   └─ 兜底      异常 / 超时 / 非法配置一律跳过
└─ 通用模块（内建于 core，向插件授予）
    ├─ git       仓库状态只读快照
    ├─ config    分层配置合并
    ├─ logger    受限日志
    ├─ events    事件落盘
    ├─ server    外部平台访问，凭据代持
    ├─ paths     路径约定
    └─ hooks     git hook 托管
        │
        ▼  单向调度
@fxdevkit/plugin-*                    插件
└─ 只依赖 sdk，彼此不可见，只使用内核授予的通用模块
```

### 1.1 两条结构约束

| 约束 | 技术手段 |
|---|---|
| 插件之间不允许互相调用 | 上下文构造时只注入该插件自身数据，不注入任何其它插件的引用、配置或导出 |
| 插件只能使用内核通用模块 | 通用模块内建于 core，不独立发包；插件通过内核注入的上下文访问，按声明权限授予 |

> 一处待明确：`sdk` 里保留了 `subscriptions`（插件可订阅符合 pattern 的事件，仅在命令执行路径激活，hook 路径不激活），这提供了一条经由内核事件总线的间接通道。它与"插件间不互相调用"铁律的边界需要单独讨论，本文先如实记录、不展开。

### 1.2 Server

当前阶段 Server 为**本地 mock**，接口契约与真实实现一致，未来切 HTTP 只需替换客户端工厂。凭据不落本地，由内核经 `exchangeCredential` 换取短期令牌。

## 二、仓库结构

```
fxdevkit/                            npm workspaces（Node 22 自带 npm，不引入 pnpm）
├── packages/
│   ├── sdk/                       @fxdevkit/sdk       插件协议类型 + definePlugin
│   ├── core/                      @fxdevkit/core      内核（调度器 + 通用模块）
│   ├── cli/                       @fxdevkit/cli       bin: fxdevkit
│   └── plugin-commit-rules/       @fxdevkit/plugin-commit-rules
└── docs/
```

依赖方向严格单向：`plugin → sdk`、`core → sdk`、`cli → core + sdk`。

- core 不依赖 cli，插件不依赖 core
- 插件之间互不可见
- **通用模块不独立发包**，因为独立发包后插件对它的引用会形成"插件依赖插件"的等价结构

## 三、插件协议（packages/sdk）

插件通过 `package.json` 的 `fxdevkit` 字段声明清单：

```json
{
  "name": "@fxdevkit/plugin-commit-rules",
  "version": "0.1.0",
  "main": "dist/index.js",
  "fxdevkit": {
    "id": "commit-rules",
    "name": "commit",
    "apiVersion": 1,
    "hooks": ["commit-msg", "prepare-commit-msg"],
    "commands": ["check"],
    "permissions": ["events:write", "git:read", "fs:repo", "proc:exec"]
  }
}
```

字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 内部唯一标识，用于配置键与事件记录 |
| `name` | 否 | 命令行短名，全局唯一，用于 `fxdevkit <name> ...`。未声明时取 `id` |
| `apiVersion` | 是 | 协议版本。内核 `PLUGIN_API_VERSION = 1`，不匹配则跳过并告警 |
| `hooks` | 否 | 订阅哪些 git 动作 |
| `commands` | 否 | 对外暴露哪些命令 |
| `permissions` | 否 | 声明所需能力 |

插件实现侧（`packages/plugin-commit-rules/src/index.ts`）：

```ts
export default definePlugin<Config>({
  id: 'commit-rules',
  defaultConfig: DEFAULT_CONFIG,
  validateConfig(raw) { /* 归一化 + 校验，非法即抛 */ },
  hooks: { 'commit-msg': async (ctx) => 'modify' | 'accept' | 'reject' | void },
  commands: { check: { describe, handler } },
})
```

`ctx` 由内核注入：`config` / `logger` / `git` / `args` / `messageFile` / `emit` / `server` / `permissions`。

## 四、内核实现（packages/core）

内核源文件按职责分为两类：**调度器**负责插件生命周期，**通用模块**向插件授予能力。

| 文件 | 类别 | 职责 |
|---|---|---|
| `plugins.ts` | 调度器 | 插件发现、版本取最新、装载、权限集合计算 |
| `kernel.ts` | 调度器 | 派发编排、上下文构造、超时、熔断、命令执行 |
| `paths.ts` | 通用模块（内核内部） | 全局目录约定，可用 `FXDEVKIT_HOME` 覆盖 |
| `hooks.ts` | 通用模块（内核内部） | dispatcher 脚本生成、`core.hooksPath` 安装与卸载 |
| `config.ts` | 通用模块 | 分层配置：源码默认（@fxdevkit/cli 包内） → 用户自定义（~/.fxdevkit/config.yaml） → 环境变量。数组整体替换，对象递归合并，用户优先。工程目录零侵入 |
| `git.ts` | 通用模块 | 仓库/分支探测、merge/rebase/cherry-pick 状态、amend 状态传递 |
| `events.ts` | 通用模块 | 事件 JSONL 落盘 |
| `server.ts` | 通用模块 | 外部平台访问：mock 实现 / HTTP 实现 / 拒绝实现 |

### 4.1 严格识别

内核在装载插件时执行三层识别。

**身份识别** —— 清单 `id` 与代码声明 `id` 必须一致，不一致拒绝装载（`loadPlugin` 里 `definition.id !== discovered.id` 返回 null）。同一 `id` 在多个目录出现时**取版本最高的一份**，其余留档在 `ignoredVersions`（版本、所在目录），使选择过程可审查；版本相同说明是同一份在多个候选目录被重复扫到（npm workspaces 符号链接），静默跳过。

**能力识别** —— 插件在清单中声明 `permissions`，内核据此构造上下文：

| 能力 | 当前行为 |
|---|---|
| `git`（快照） | **只读、无害，当前无条件注入**真实 `GitContext` |
| `events:write` | 声明则注入真实 emitter（事件落盘），未声明注入静默实现 |
| `net:server` | 声明则注入 Server 客户端，未声明注入拒绝实现（调用即记录告警） |
| `fs:repo` / `fs:global` / `git:write` / `proc:exec` | 声明式预留，当前无强制点 |

未声明即授予空实现而非抛出错误——插件可据此自行降级，不必做权限判断。

**边界识别** —— 上下文只注入该插件自身的配置与状态。内核不暴露插件列表，插件无法获得其它插件的任何引用。

### 4.2 插件发现

`discoverPlugins` 扫描以下目录（`packages/core/src/plugins.ts` 的 `candidateDirs`），按 `id` 去重、按版本取最新：

1. `<repo>/node_modules/@fxdevkit`
2. `<repo>/node_modules`
3. `~/.fxdevkit/plugins`
4. `~/.fxdevkit/node_modules/@fxdevkit`
5. `FXDEVKIT_PLUGIN_PATHS` 指定目录
6. CLI 自身安装位置的 `node_modules`（从内核文件位置逐级向上找 `@fxdevkit` scope）

匹配包名前缀 `@fxdevkit/plugin-*` 或 `fxdevkit-plugin-*`。

### 4.3 hooks 托管：全局一次 + 仓库显式停用

**问题**：早期设计是「逐仓库设 `core.hooksPath`」——但新仓库、克隆的仓库、临时仓库都不会生效，用户必须记得在每个仓库执行一次 `install`。结果「增强看起来像手动触发」。

**方案（已采纳）**：拆成两层，但**默认是增强**。

| 层 | 存储位置 | 命令 | 作用 |
| --- | --- | --- | --- |
| 全局 | `git config --global core.hooksPath` | `fxdevkit install --global` | 一次设置，所有仓库（含以后新建的）都走 dispatcher |
| 仓库（停用） | `git config fxdevkit.enabled=false` | `fxdevkit uninstall` | 当前仓库**显式停用**——默认是不写标记（启用） |

**语义翻转**：装上全局 hooks 后，**所有仓库默认都被增强**。`isRepoEnabled` 的判定从「`=== 'true'` 才启用」改为「`!== 'false'` 才启用」。个别仓库想停用才用 `fxdevkit uninstall`；重新启用用 `fxdevkit install`（覆盖停用标记）。目录收窄优先用插件的 `projects` 作用域（见 §4.5），不要用 `uninstall`——后者相当于全局一刀切。

**迁移**：旧版本给每个仓库单独设 `core.hooksPath`。仓库级的值会盖住全局值，
所以 `enableRepo` 检测到后会清除它。注意必须用 `--local --get` 读取——
不带作用域的 `--get` 会回退读到全局值，导致新仓库被误判为「需要迁移」，
进而去 unset 一个并不存在的键而报错。

### 4.4 分层执行：不取缔仓库自有 hooks

git 的 `core.hooksPath` 是**替换**语义：指向 fxdevkit 后，仓库自己的 `.git/hooks/<name>`
原本就不会再被执行。dispatcher 主动补上这一层：

```
git 触发 <hook>
  ↓
① 仓库自有：<repo>/.git/hooks/<hook>  存在且可执行则先执行
     ├─ 返回非零  → 阻断（尊重 git 原生语义，不再跑增强）
     └─ 返回 0 / 不存在 → 继续
  ↓
② 总开关：本仓库 fxdevkit.enabled === true ？
     └─ 否 → 放行（不增强，但 ① 已经执行过了）
  ↓
③ 用户级：按作用目录过滤插件后派发
     └─ 插件显式 reject → 阻断；其余一律放行
```

要点：

- **自有 hook 压根执行不起来**（解释器缺失、权限问题）→ 返回 `null` 按放行处理，
  绝不能因为「跑不起来」把用户的提交卡住。
- **Windows 不能直接 spawn 带 shebang 的脚本**：`CreateProcess` 不认 `#!/bin/sh`，
  cmd.exe 会报「不是可运行的程序」。`resolveRunner` 先解析 shebang 取出解释器
  （`sh` / `bash` / `node` …，含 `#!/usr/bin/env bash` 形式），再把脚本路径作为参数传入。
- 仓库里原本装了 husky / lefthook / 自定义 hook 的，**照常执行，不被取缔**。

### 4.5 插件作用目录（scope）

插件可声明「只在哪些目录下生效」，写在 `~/.fxdevkit/config.yaml`：

```yaml
plugins:
  commit-rules:
    enabled: true
    # 不写 projects → 全局生效
  api-sync:
    enabled: true
    projects:
      - D:/products/order-service   # 只在该目录及其子目录下的仓库生效
```

判定在 `packages/core/src/scope.ts` 的 `pluginScope()`，由内核完成，**插件自身不感知**：

- 未配置 `projects` 或为空数组 → 全局生效
- 已配置 → 仓库根目录须位于其中某目录或其子目录下（路径前缀匹配，
  Windows 下大小写不敏感）
- 不在作用目录内 → 跳过该插件，`status` 显示「未生效」并给出原因；
  `doctor` 判定为**通过**（这是配置预期，不是故障）

### 4.6 按需解析（当前实现）

内核只在调度到某个动作时，才解析该动作所需的插件。`dispatchHook` 用 `selectPlugins(discoverPlugins(repoRoot), hookName)` 过滤出声明了该 hook 的插件，逐个装载执行。

**当前缺失行为：静默放行。** 没有候选插件时直接放行，不提示、不安装。安装是网络操作，耗时不可控，不能塞进 hook 的同步阻塞路径。

安装由用户显式触发，用 `plugin add` 装到用户目录：

```bash
fxdevkit plugin add @fxdevkit/plugin-commit-rules
```

`plugin add` 内部即 `npm install <pkg>` 到 `~/.fxdevkit`。

> **规划中的能力（未实现）**：早期设计里有「仓库声明 `requires` + `fxdevkit plugins --sync` 按声明补齐」。当前代码没有落地 `requires` 声明与 `--sync` 命令，暂以 `plugin add` 手动安装替代。是否需要恢复该设计，待定。

### 4.7 amend 状态传递

`commit-msg` hook 拿不到命令行参数，无法自行判断 `--amend`；只有 `prepare-commit-msg` 能拿到 `source` 与 `commit sha`。

因此：

- `prepare-commit-msg`：识别 amend 并写入 `~/.fxdevkit/cache/commit-state.json`
- `commit-msg`：消费并清除该状态

### 4.8 日志追踪（双通道）

**为什么**：调试"插件到底跑没跑"、"为什么 commit 没生效"、"事件之间的顺序"——必须有一份完整且可查询的轨迹。

**通道设计**（`packages/core/src/logger.ts`）：

| 通道 | 谁写 | 内容 |
|---|---|---|
| `core` | kernel 调度器 | 「派发 hook · 仓库 X」「候选插件 N 个」「[id] 执行」「[id] 完成：modify」 |
| `plugin` | 插件通过 `ctx.logger` | 插件自己的输出 |

**落盘**：每天一个文件 `~/.fxdevkit/logs/YYYY-MM-DD.log`，每行一条 JSON 记录。

**打印策略**：

| 级别 | hook 路径 | 命令路径 | 落盘 |
|---|---|---|---|
| error | stderr | stderr | ✅ |
| warn | stderr | stderr | ✅ |
| info | 只落盘 | stderr + 落盘 | ✅ |
| debug | 只落盘（需 `FXDEVKIT_DEBUG=1`） | 同上 | ✅ |

**为什么 hook 路径默认静默**：避免每次 commit 刷屏。`fxdevkit logs` 可随时拉出来看。

**环境变量控制**：`FXDEVKIT_DEBUG=1`（全打 stderr）、`FXDEVKIT_LOG_LEVEL`（阈值）、`FXDEVKIT_LOG=0`（关落盘）。

**查看命令**：

```bash
fxdevkit logs                       # 今天全部
fxdevkit logs --core                # 只看内核调度日志
fxdevkit logs --plugin commit-rules # 只看某插件
fxdevkit logs --level error         # error 及以上
fxdevkit logs --day 2026-09-08      # 指定日期
fxdevkit logs --days                # 列出所有日志文件
fxdevkit logs --last 20             # 只看最后 20 条
```

### 4.9 Cursor GUI 兼容（git wrapper）

**问题**：Cursor 3.15.6+ 的 git 扩展在每次调用 git 时通过环境变量强制注入 `core.hooksPath=/dev/null`（Windows 上是 `NUL`），导致 Source Control 面板的所有 git 操作（commit / push / status 等）都被静默跳过 hooks。Cursor 官方已确认是 bug。

**关键发现**：该覆盖走的是 `GIT_CONFIG_KEY_n` / `GIT_CONFIG_VALUE_n` 环境变量，优先级最高，`git config --global core.hooksPath` 无法对抗。命令行 git（终端里）不受影响——Cursor 只覆盖自己 spawn git 的环境。

**解法**：给 Cursor 配一个 git wrapper，删掉 `core.hooksPath` 这条覆盖再转发给真 git。

**实现**（`scripts/git-hooks-restore.cjs` + `scripts/git-hooks-restore.exe`）：

- 逻辑：从 `process.env` 读 `GIT_CONFIG_COUNT` 和 `GIT_CONFIG_KEY_n` / `GIT_CONFIG_VALUE_n`，删掉 `core.hooksPath` 这一对，重建环境变量后 spawn 真 git（默认 `D:\softs\Git\bin\git.exe`，可用 `FXDEVKIT_REAL_GIT` 覆盖）。stdio `inherit`，exit code / signal 透传。
- 打包：用 `pkg` 把 `.cjs` 打包成单文件 exe（37MB），让 Cursor 看到的就是一个真·git 可执行文件，避开 array 解析问题。

**Cursor 配置**（写入 `%APPDATA%\Cursor\User\settings.json`）：

```json
"git.path": "D:\\products\\devkit\\scripts\\git-hooks-restore.exe"
```

**前置条件**：必须用 **multi-root workspace**（`.code-workspace`）打开多个仓库，不能直接打开父目录（如 `D:\projects`）——父目录本身不是 git 仓库，Cursor 会显示「没有 Git 存储库」。

**坑**（踩过的）：
- `git.path` **必须用 string + exe 路径**，不能用 array `["node.exe", "wrapper.cjs"]` 形式——Cursor 3.19 对 array 解析有问题，会把 git 集成一并搞挂。
- wrapper 必须用 `.cjs` 扩展名，因为 devkit 的 `package.json` 是 `type: "module"`。
- wrapper 写诊断日志到 `~/.fxdevkit/logs/wrapper.log`，便于排查。

**回滚**：删 `settings.json` 里的 `git.path`。

## 五、commit-rules 插件

### 5.1 commit-msg 执行流程

```
读取提交信息文件
  ↓
[守卫] merge / rebase / cherry-pick / amend → 放行
  ↓
[守卫] 分支不在 scope 内 → 放行
  ↓
[规则匹配] 有 pattern 的规则按顺序短路
  ├─ 命中 skip   → 放行
  ├─ 命中注入型  → 改写
  └─ 无命中      → 应用兜底规则
  ↓
写回文件（dryRun 时不写）
```

### 5.2 幂等性交叉校验

兜底规则注入的前缀，必须能被某条 skip 规则匹配，否则同一条 message 被二次处理会变成 `AI AI xxx`。

`validateConfig` 阶段做静态探测：用兜底规则的 value 拼一条探针 message，检查是否有 skip 规则能匹配；不能则直接抛错，并给出建议 pattern。

### 5.3 默认配置

```yaml
plugins:
  commit-rules:
    rules:
      - name: ai-explicit
        pattern: '^(AI|ai)[:\s]'
        action: skip
      - name: no-ai
        pattern: '^(chore|docs|merge|revert)[:\s]'
        action: skip
      - name: default
        action: prefix
        value: 'AI '
    branches: ['*']
    dryRun: false
```

### 5.4 CI 侧强制

```bash
fxdevkit commit check --sha <sha>
```

校验提交信息，不修改任何内容，不合规返回 1。`check` 通过插件 `name`（`commit`）路由，等价于 `fxdevkit run commit-rules check` 的旧写法已废弃。

本地 hook 能被 `git commit --no-verify` 绕过，真正的强制要落在 CI。

## 六、命令

> 完整用法与真实输出见 `命令手册.md`。此处只列命令结构。

```bash
fxdevkit -v                         版本
fxdevkit --help                     帮助
fxdevkit status                     当前状态：版本 / 仓库 / hooks / 插件
fxdevkit doctor                     环境与链路自检
fxdevkit install                    启用当前仓库增强（fxdevkit.enabled）
fxdevkit install --global           安装全局 hooks（core.hooksPath，一次）
fxdevkit uninstall                  停用当前仓库增强
fxdevkit uninstall --global         卸载全局 hooks
fxdevkit update [version]            更新 / 回退自身
fxdevkit plugin list                列出内核发现的插件
fxdevkit plugin add <pkg>           安装插件到 ~/.fxdevkit
fxdevkit plugin remove <pkg>        移除插件
fxdevkit plugin enable <id>         启用插件
fxdevkit plugin disable <id>        停用插件
fxdevkit config show                查看生效配置（分层来源）
fxdevkit config validate            校验插件配置
fxdevkit report                     本地事件统计
fxdevkit <name> -v                  查看插件版本
fxdevkit <name> --help              查看插件命令
fxdevkit <name> <cmd> [args]        执行插件命令
```

### 6.1 CLI 不认识插件 id

`fxdevkit <name> <cmd>` 是通用路由（`packages/cli/src/index.ts` 的 `default` 分支）。CLI 只做参数转发，具体插件短名由用户在命令行给出，CLI 源码中不出现任何业务插件 id。插件命令来自插件自身的 `commands` 声明，未提供某命令时会提示、不静默通过。

例如插件提供的提交信息校验：

```bash
fxdevkit commit check --sha HEAD
```

### 6.2 插件手动安装

内核不代用户安装插件。用户自行用 npm 安装，内核负责发现：

```bash
npm i -D @fxdevkit/plugin-commit-rules     装到仓库，仅当前项目可见
npm i -g @fxdevkit/plugin-commit-rules     装到全局，所有项目可见
fxdevkit plugin add <pkg>                  装到 ~/.fxdevkit（等价 npm install 到用户目录）
```

| 安装位置 | 是否被发现 |
|---|---|
| `<repo>/node_modules/@fxdevkit/plugin-*` | 是 |
| `<repo>/node_modules/fxdevkit-plugin-*` | 是 |
| 全局 `node_modules/@fxdevkit/plugin-*` | 是 |
| `~/.fxdevkit/plugins` / `~/.fxdevkit/node_modules` | 是 |
| `FXDEVKIT_PLUGIN_PATHS` 指定目录 | 是 |

因此不需要安装器、启停状态机与来源记录——插件的可见性完全由安装位置决定。

### 6.3 hook 自愈

`post-checkout` 时若检测到全局 `core.hooksPath` 不再指向 fxdevkit（`needsReinstall`），且当前仓库已启用，则自动重装全局 hooks——解决 clone 后 hook 丢失的问题。

### 6.4 熔断模型

插件错误不得阻断研发动作，三层保障：

- **脚本层**：dispatcher 退出码只有 `1` 才阻断，其余一律放行
- **内核层**：`dispatchHook` 在任何异常路径下都返回 0；插件抛异常、超时（`config.hooks.timeoutMs`，默认 1000ms）、配置非法一律跳过，只有显式 `reject` 才返回 1
- **入口层**：hook 路径下未捕获异常强制退出 0（`invokedAsHook` 判断）
