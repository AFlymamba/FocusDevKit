怎么用

三种入口，一条内核

你想怎么用它都行，背后是同一条调度链路，装一次，三种都通。

自动触发　你不用记得做任何事

照常提交代码，规范校验、前缀补全、行为记录在背后一次完成。它只在该出现的时候出现，其余时候你感觉不到它。

主动触发　一条命令看清全局

状态、健康、日志、事件都在手边。想确认增强有没有生效、命中了什么规则，不用猜，直接查。

对话触发　说一句话就够

你描述意图，AI 去调用插件的 skill 与 MCP。演进方向，契约位置已经留好。

为什么

增强这件事，不该每次都重做一遍

想让工具替你多干一点，通常只能零散地加：一段 hook 脚本、一条 lint 规则、一个 CI 步骤。每加一种，就重新接一次。

零散增强的三个代价

  • 重复——每种增强都要自己解析上下文、自己读配置
  • 不一致——有的失败会阻断，有的静默放行，行为无法预期
  • 不可见——做过什么、命中过什么，事后无从追溯

统一挂载点给的是什么

  • 接入一次，之后每增加一种增强就是装一个插件
  • 失败策略统一：一律跳过放行，绝不打断你手上的事
  • 每一次增强都留下记录，可查、可回溯

四层结构

单向依赖。插件只依赖契约，彼此不可见，可以单独安装、单独演进、单独交付。

CLI　命令层
你敲的命令。命令集与插件无关，插件增减不改变它。
Core　内核
调度器（发现 / 装载 / 派发 / 兜底）+ 通用模块。不实现任何能力，不含领域语义。
Plugin　插件
每个插件是一个独立的 npm 包。
SDK　契约
插件与内核之间唯一的依赖，只有类型与协议。

当前能力

0.1.0 已经跑通的

第一个插件是 commit-rules：自动给 commit message 补上团队约定的前缀，跳过 merge / rebase / cherry-pick，并把每次增强的命中与结果记录下来。它的作用是验证全链路——让你看到加第二个插件有多便宜。

  • 通用 hookscommit-msg、prepare-commit-msg、pre-commit、pre-push、post-checkout、post-merge
  • 一次安装，全部生效install --global 之后所有仓库默认被增强，单个仓库可随时停用
  • 作用域插件只在指定目录生效，判定由内核完成，插件无感
  • 看得见双通道日志按天落盘，增强行为按月归档，事后可追溯
  • 权限模型插件声明所需权限，未声明的能力给空实现而非报错，可降级运行
  • 不取代现有工具与 husky / lefthook 共存，仓库自有 hook 优先，原有链路照常执行

上手

三步，之后你不会再想起它

# 1. 全局安装
npm install -g @fxdevkit/cli

# 2. 挂载全局 hooks（一次，之后所有仓库默认被增强）
fxdevkit install --global

# 3. 装你需要的插件
fxdevkit plugin add @fxdevkit/plugin-commit-rules

之后照常工作。想知道它做了什么：

fxdevkit status          # 当前仓库：hooks、插件、是否启用
fxdevkit doctor          # 健康检查
fxdevkit logs --last 20  # 最近的调度日志

用户配置在 ~/.fxdevkit/config.yaml，跟人走、跨升级保留。工程目录零侵入，不需要往仓库里加任何文件。

边界

不做的事，同样写进设计

每一条边界，都对应一项你不必承担的成本。

不做因此不必承担
不替使用者决策增强自动发生，决定权始终留在你手里
不做团队管控没有流程约束，没有策略下发，不为协作场景引入任何配置
不做插件编排插件各自独立，装一个不影响另一个，也不必排加载顺序
不代装插件装什么、装几个由你决定；内核只负责发现，不发起网络请求
不为想象中的需求写代码没有预置的签名、市场与状态机——用不到时，它们都是净成本

对话触发、AI 大脑、MCP 接入已经进入视野。契约位置留着，实现等真实需求。
