# dev-kit 产品定义

> 本文是当前对齐后的产品意图结论。
> 最后更新：2026-09-03

---

## 一、真正的产品意图

**dev-kit 的第一目标不是做大平台，而是快速解决你自己的高频痛点，持续给你提效。**

换句话说：

- 先解决真实、具体、重复发生的问题
- 先做能立刻释放你的东西
- 先追求“好用、顺手、见效快”
- 平台化、团队化、治理化都放在后面

所以它的正确定位不是“研发流程中台”，而是：

> **一个以个人研发提效为起点、可无限扩展且可控的插件式开发工具。**

---

## 二、产品原则

### 1. 先痛点，后平台

顺序必须是：

1. 先解决一个真实痛点
2. 形成一个稳定插件
3. 再抽象出共性内核能力
4. 最后才谈平台能力扩展

不是先搭一个大平台，再往里塞场景。

### 2. 一切皆插件

所有具体能力都应该是插件：

- commit 前缀处理
- API 同步
- 自测辅助
- 提测单生成
- 发布检查
- 后续任何研发提效动作

**业务能力不进内核，全部插件化。**

### 3. 内核只做管理，不自动装配业务插件

内核只负责这些事情：

- 插件安装、卸载、启停
- 插件发现与加载的基础能力
- 插件配置管理
- 插件版本管理
- 插件调用路由与基础运行时
- 插件列表查询

但要明确一条：

> **内核不应该主动去替你装配业务插件，更不应该默认加载一堆扩展。**

如果某个能力必须挂到内核上，那也应该是：

1. 先让内核以最小形态启动
2. 再由用户明确决策是否加载某个插件
3. 插件是否进入内核运行面，由用户说了算

内核不负责：

- commit 语义
- 需求流程
- 测试流程
- 发布流程
- Apifox 业务逻辑
- AI 业务逻辑

**内核只认识插件，不认识业务。**

### 4. 无限扩展，但必须可控

“无限扩展”不是放任增长，而是：

- 新能力可以不断加
- 每个能力以插件独立演进
- 内核边界不被污染
- 插件可启停、可替换、可观察

所以关键词不是“大而全”，而是：

> **小步快跑 + 插件扩展 + 核心可控**

---

## 三、第一版 MVP

### MVP 目标

第一版只做一件事：

> **先把你最烦、最高频、最明确的痛点做顺，直接开始省时间。**

### MVP 范围

#### 1. 内核：最小启动

第一版内核只保留最小能力：

- 能启动
- 能接收用户明确操作
- 能装载用户选择的插件
- 能更新插件
- 能卸载插件
- 能列出当前可用插件

先不做：

- 使用用户统计
- 注册人数统计
- 优先级编排
- 流程编排
- 复杂 Server 管控
- 默认加载一堆扩展插件

**内核先跑起来，但不要替用户做插件决策。**

#### 2. 第一个插件：git commit 判定补充

第一版先做 commit 相关插件，但要收敛成最小可用：

- 判定当前 commit 是否需要补前缀
- 如果用户已经手工加了规则，就直接跳过
- 规则可配置
- 幂等，不重复注入
- 以不打断开发为前提

#### 3. 插件不做优先级

第一版**不做插件优先级**。

原因很简单：

- 优先级本质上是编排
- 一旦开始编排，就进入另一个产品链路
- 这会把第一版从“提效工具”拖成“流程引擎”

所以第一版采用：

> **插件自己装配，自己按约定执行，不做优先级调度。**

---

## 四、用户怎么上手

### 上手目标

用户第一次接触时，不应该先理解一整套体系，而是：

1. 安装最小内核
2. 看见插件列表
3. 自己选择装哪个插件
4. 自己决定是否启用
5. 先跑第一个插件

### 上手路径

#### 1. 安装 dev-kit

先把 `devkit` 装到本地，让它能运行命令。

#### 2. 看插件列表

用 `devkit plugin list` 看当前能用的插件。

#### 3. 安装想用的插件

用 `devkit plugin add <pkg>` 把插件装进去。

#### 4. 自己决定启用或禁用

用 `devkit plugin enable <id>` / `devkit plugin disable <id>` 控制插件是否进入运行面。

#### 5. 先用第一个插件

先从 commit 相关插件开始，马上看到效果。

---

## 五、安装方式（最小方案）

### 1. CLI 安装

当前主入口就是 CLI。用户装好后，直接用命令操作。

### 2. 插件安装

插件通过 npm 包安装到本地插件目录，再由内核发现。

### 3. 用户手动选择

内核不默认帮用户加载一堆插件，用户自己决定装什么、启什么。

### 4. 最小闭环

最小闭环就是：

- 安装 devkit
- `plugin list`
- `plugin add`
- `plugin enable`
- 执行第一个插件

## 六、当前阶段的正确节奏

### 当前应该做

1. 先把内核做成最小启动形态
2. 先把第一个插件做顺
3. 先验证“你真的会用，而且真的省时间”
4. 再考虑第二个插件

### 当前不应该做

1. 不做优先级编排
2. 不做流程引擎
3. 不做大平台治理
4. 不做复杂团队统计
5. 不为了未来想象提前堆能力

---

## 七、当前确认的起点

### 起点 1：commit-rules

这是当前最适合作为第一插件的场景。

目标不是“AI 统计体系”，而是：

- commit 时自动补前缀
- 如果你已经手工加了规则，则跳过
- 规则可配置
- 幂等，不重复注入
- 尽量无感，不打断开发

它是一个典型的“高频、刚需、立刻见效”的个人提效插件。

### 起点 2：api_sync_to

这是第二类能力的代表：

- 你不想被某个平台的接入方式绑死
- 你想保留自定义目标的能力
- 你要的是“同步到某处”的通用能力，而不是“专门适配某个平台”

所以它应该从一开始就设计成：

> `api_sync_to <target>`

而不是直接写死为某个平台插件。

---

## 八、CLI + Server 的正确理解

从长期看，dev-kit 可以拆成 CLI + Server，但在当前阶段，它们的优先级不同。

### CLI 是现在的重点

CLI 负责：

- 直接在你本地执行
- 接住你的高频动作
- 快速提供提效价值
- 承载插件运行

### Server 是为“可控扩展”预留的

Server 的价值主要在未来这些事情上：

- token 代持
- 插件注册与分发
- 使用统计
- 团队策略
- 权限与审计

所以我的判断是：

> **当前阶段以 CLI 为主，Server 只保留扩展位，不抢主线。**

---

## 九、MVP 边界

### 当前应该做

1. 先把 `commit-rules` 做到稳定可用
2. 插件协议要尽早定下来
3. 内核只保留最小管理能力
4. 后续插件按“是否真的省你时间”来排优先级

### 当前不应该做

1. 不先做大而全流程平台
2. 不先做复杂团队治理系统
3. 不先做完整 Server 管控面
4. 不为了抽象而抽象
5. 不把少数未来场景提前塞进内核

---

## 十、我对 dev-kit 的一句话定义

> **dev-kit 是一个从个人研发提效出发、以插件为能力载体、以内核管理保证可控扩展的开发工具。**

简化一点，就是：

> **先解放你，再逐步长大。**

---

## 十一、下一步建议

接下来产品层面不再发散到“大平台”，而是只做三件事：

1. **定义第一版 MVP 边界**：第一版只做什么，不做什么
2. **排第一批插件优先级**：先做 commit-rules，再决定第二个插件
3. **收敛最小内核能力**：只保留支撑插件增长所必需的管理能力
