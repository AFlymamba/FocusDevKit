# fxDevKit

一个面向研发阶段的插件化增强器。

## 它解决什么问题

研发工作天然会经历多个阶段：提交、同步、自测、检查、交付，以及阶段之间的衔接。
这些阶段本身无法回避，但每个阶段背后的规则、补充动作与上下文切换，都会持续消耗注意力。

fxDevKit 的目标，不是重做研发流程，而是在研发阶段背后提供增强：
- 在不同阶段补足规则与能力
- 在现有流程之上增加可扩展的增强层
- 减少上下文切换与重复摩擦
- 让研发者把精力重新放回代码本身

## 它如何工作

fxDevKit 以插件方式组织能力。

你不需要迁移到一套全新的工作流，只需要在现有研发阶段背后启用对应插件：
- 提交阶段的规则增强
- 接口同步阶段的能力增强
- 自测阶段的辅助增强
- 发布前检查阶段的校验增强
- 后续其他研发阶段的扩展增强

## 核心目标

fxDevKit 追求的不是“少做研发动作”，而是：
- 让既有阶段更顺手
- 让不同阶段获得针对性的增强
- 让研发者从重复性干扰中释放出来
- 让能力可以持续扩展，但始终保持可控

## 一个最小例子

`git commit` 这件事你本来就会做，也绕不过去。

fxDevKit 不改变这件事本身，而是在提交阶段背后提供增强：
- 规则可配置
- 已有规则可识别并跳过
- 后续可继续扩展更多提交增强能力

也就是说，它不是替代 `git commit`，而是增强 `git commit`。

## 核心思路

### 1. 按研发阶段做增强

fxDevKit 关注的是研发过程中的不同阶段，而不是先做一套全新的流程系统。

### 2. 一切皆插件

所有具体能力都应该以插件形式存在：
- 提交规则增强
- 接口同步增强
- 自测增强
- 发布检查增强
- 后续任何阶段性增强

### 3. 内核只负责管理

内核只负责：
- 插件安装
- 插件加载
- 插件更新
- 插件卸载
- 插件启用 / 禁用
- 插件列表查询

内核不负责业务语义，不替研发者做流程决策。

## 当前方向

fxDevKit 从最小能力开始，先把一个真实痛点做顺，再逐步把更多阶段性的增强能力沉淀为插件。

README 会随产品持续迭代更新，它描述的是当前阶段的 fxDevKit，而不是一个预设终局。
