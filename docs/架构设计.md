# fxDevKit 架构设计

> 文档定位：**用户视角**的概念与设计决策。
>
> 配套 `docs/详细设计.md`（实现视角、数据流、API、调用链）。
>
> 本文件回答三个问题：**fxDevKit 是什么**、**你用它要做什么**、**它跟别的东西怎么配合**。
>
> 不涉及具体函数签名与代码实现细节——那部分在《详细设计》。

---

## 0. 一句话定位

**fxDevKit 是一套研发动作增强器**：你照常敲命令（`git commit`、`git push`、`fxdevkit status`……），系统在关键时刻插入结构化的检查、修改、记录能力。它不替代 git、不接管你的代码，纯粹"挂在动作背后"。

---

## 1. 用户视角：你只需要知道这三件事

> 这一节是文档核心。从用户出发，不讲系统内部路径。

### 1.1 输入命令（你照常敲命令）

你敲的所有命令都归为两类，**对你来说都是命令**：

| 你敲的命令 | 系统做了什么 |
|---|---|
| `git commit -m "..."` | 系统在 git 执行 commit 前/后跑一遍插件 |
| `git push` | 系统在 git 执行 push 前/后跑一遍插件 |
| `fxdevkit status` / `doctor` / `logs` | 系统告诉你当前状态 |
| `fxdevkit run <plugin> <cmd>` | 系统调起某个插件的命令 |
| `fxdevkit install [--global]` | 系统装好 hooks / 启用当前仓库 |
| `fxdevkit uninstall [--global]` | 反向 |

**对用户而言**：你敲什么命令就是什么命令，没有「两条路径」这种区分——这是系统内部的实现细节。

### 1.2 配合授权（系统需要你给什么）

系统正常运行需要你授权以下内容，**都是一次性的**：

| 授权 | 你做什么 | 为什么要 |
|---|---|---|
| **git hooks 授权** | 跑一次 `fxdevkit install --global` | 让所有仓库的 git hook 都先经过系统，并**默认全部增强** |
| **停用某仓库（可选）** | 在该仓库跑 `fxdevkit uninstall` | 默认全局生效，只有显式停用的仓库才例外 |
| **插件权限** | 插件 manifest 里声明 `permissions` | 没声明的能力 → 给空实现（不报错） |
| **作用域（可选）** | 在 `~/.fxdevkit/config.yaml` 配 `plugins.<id>.projects` | 不配 = 全局生效；配了 = 只在指定目录生效 |

**核心语义：装一次全局 hooks，所有仓库默认增强**。目录收窄优先用插件的 `projects` 作用域；只排除个别仓库时才用 `fxdevkit uninstall`。系统不会自动改你的 git config、自动装插件。

### 1.3 看反馈（你想知道什么，就用什么命令）

| 你想知道 | 用什么命令 |
|---|---|
| 系统是否健康 | `fxdevkit doctor` |
| 当前仓库状态 | `fxdevkit status` |
| 谁被执行了 / 结果如何 | `fxdevkit logs` |
| 某个插件的日志 | `fxdevkit logs --plugin <id>` |
| 事件统计 | `fxdevkit report` |

设计取舍：正常 commit 时**终端完全静默**——不打扰你的提交节奏。日志默认只落盘（`~/.fxdevkit/logs/`），要看就 `fxdevkit logs` 拉出来。

## 2. 系统由什么构成（四层）

四个层级，**单向依赖**，每层只有一种职责：

| 层 | 是什么 | 用户视角对应 |
|---|---|---|
| **CLI** | 子命令解析、输出格式化 | 你敲 `fxdevkit ...` 时的翻译层 |
| **Core** | 调度器 + 10 个通用模块 | 系统的"大脑"——知道找插件、装载、派发 |
| **Plugin** | 一个或多个独立 npm 包 | 具体做事的人，每个都能独立替换 |
| **SDK** | Core 与 Plugin 之间的协议 | "插件长什么样、ctx 里有什么"的契约 |

```
+---------------------------------------------------+
|  你敲的命令                                         |
|    git commit / fxdevkit run / fxdevkit status     |
+---------------------------------------------------+
                        |
                        v
+---------------------------------------------------+
|  CLI 层  (packages/cli)                            |
|    子命令解析 + 帮你格式化输出                      |
+---------------------------------------------------+
                        |
                        v
+---------------------------------------------------+
|  Core 层  (packages/core)                          |
|    调度器（找插件 / 装插件 / 授权 / 派发）         |
|    10 个通用模块（git / 配置 / 日志 / 事件 ...）   |
+---------------------------------------------------+
                |               |
                v               v
+---------------------------------------------------+
|  Plugin 层  (packages/plugin-*)                    |
|    每个插件 = 一个独立 npm 包                       |
|    唯一依赖：@fxdevkit/sdk                          |
+---------------------------------------------------+
                        ^
                        | (契约)
+---------------------------------------------------+
|  SDK 层  (packages/sdk)                             |
|    定义插件长什么样、ctx 里有什么                   |
+---------------------------------------------------+
```

### 2.1 三条不可违反的约束

| 约束 | 含义 |
|---|---|
| **单向依赖** | CLI → Core；Plugin → SDK；Plugin 不依赖 Core 或 CLI |
| **插件独立** | 插件之间不互相调用、不互相 require |
| **Core 不代笔** | Core 只编排，不替插件写文件/落事件——动手的事给插件 |

## 3. 核心概念（你需要理解的 4 个）

### 3.1 插件（Plugin）

**插件是系统的可变部分**。所有具体能力（commit 检查、依赖审计、接口同步……）都由插件承担。

- 插件 = 一个独立 npm 包，名字带 `plugin-*` 或 `fxdevkit-plugin-*`
- 插件在两处声明自己：`package.json` 的 `fxdevkit` 字段（manifest）+ 代码里的 `definePlugin({...})`
- 两处 `id` 必须一致，否则系统丢弃
- 插件不依赖 core，不依赖其他插件
- 删一个插件 = `rm -rf packages/plugin-<name>`，无需卸载命令

### 3.2 内核（Core）

**内核是系统的不变部分**。它做四件事：

1. **发现** —— 从 node_modules 找插件
2. **装载** —— 加载插件代码
3. **授权** —— 检查权限，构造 ctx（上下文）
4. **派发** —— 在 git hook 时刻或 fxdevkit 命令时刻调插件

除此之外内核不做事。它不写你的文件、不替你 commit、不替你发请求。

### 3.3 契约（SDK）

**SDK 是内核和插件之间的唯一协议**。插件作者只需 `import { definePlugin } from '@fxdevkit/sdk'`，剩下的事（ctx 构造、派发）由内核做。

SDK 只声明、不动手：不发请求、不读文件、不 spawn 子进程。

### 3.4 授权（Permissions）

插件要做什么事，必须先在 manifest 里声明 `permissions`。**未声明的能力 = 空实现**：

| 声明 | 拿到什么 | 没声明拿到什么 |
|---|---|---|
| `fs:repo` | 仓库内读写 | 空 |
| `fs:read` | 只读 | 空 |
| `events:write` | `ctx.emit` 可用 | 静默函数 |
| `net:server` | `ctx.server` 可联网 | 拒绝客户端 |
| `git:write` | git 写操作（amend/rebase） | 空 |

**这是安全边界的核心**：插件拿不到没声明的东西，**也不会因为没声明而崩**。它优雅降级。

## 4. 一次请求的完整流程（用户视角讲故事）

> 用一个真实场景把上面三件事串起来。**这是用户视角，不画内部架构图**。

### 4.1 场景：在 `devkit` 仓库改了点代码，准备 commit

**第一步（命令）**：你在终端敲
```bash
git commit -m "fix: 修复XX"
```

**第二步（系统做了什么）**：
1. git 看 `core.hooksPath` 指向 `~/.fxdevkit/hooks/`
2. git 跑 `~/.fxdevkit/hooks/commit-msg <msg-file>` —— 这只是个一行 shim：`exec fxdevkit hook commit-msg "$@"`
3. fxdevkit 收到，调内核 → 内核找插件 → 插件检查提交信息、加 `AI ` 前缀 → 写回文件 → 返回 0
4. git 看到 exit 0，用改写后的 message 完成 commit

**第三步（你看到什么）**：
- 终端**完全静默**（没打断你）
- 但 message 已经被加了 `AI ` 前缀
- 全程有日志落到 `~/.fxdevkit/logs/2026-09-07.log`

### 4.2 场景：你想知道刚才 commit 都发生了什么

**命令**：
```bash
fxdevkit logs --core --last 10
```

**输出**（简化）：
```
10:50:17  core  info  派发 commit-msg · 仓库 D:/products/devkit
10:50:17  core  info  声明 commit-msg 的候选插件 1 个
10:50:17  core  info  [commit-rules] 执行 commit-msg
10:50:17  core  info  [commit-rules] 完成：modify
```

这就是用户视角的整个系统：**敲命令 → 看日志**。至于"hook 路径还是命令路径"、"插件生命周期几阶段"，是系统内部的事，跟你的日常使用没关系。

## 5. 什么时候用 fxDevKit、什么时候不用

### 5.1 适合用

- 团队对 commit message 格式有规范，想强制落地
- 想自动记录"这次提交触发了什么"
- 多个项目共享同一套研发动作约束
- 想要在不动业务代码的前提下，给流程加钩子

### 5.2 不适合用

- 想要取代 git/IDE 的（这是增强器，不是替代品）
- 想在仓库里塞业务代码的（fxDevKit 不接管业务代码）
- 想要一个"装上就能自动配好一切"的工具（系统不自动安装、不自动启用）

### 5.3 跟 husky/lefthook 怎么配合

- **husky/lefthook**：项目级 hook 管理（在 `<repo>/.git/hooks/` 或 `.husky/`）
- **fxDevKit**：跨项目的 hook 入口（全局 `~/.fxdevkit/hooks/`）+ 插件派发

**fxDevKit 内部**保留了仓库自有 hook（`runRepoOwnHook`），所以 husky/lefthook 装了照样能跑——它们是项目级 hook，fxDevKit 是分发层。两者**共存而非替代**。

## 6. 核心设计决策（已拍板）

| 决策 | 取舍 | 文档位置 |
|---|---|---|
| 插件之间不互相调用 | 强隔离；通过事件订阅做间接联动 | §2.1 / §3.4 |
| Core 不替插件动手 | 编排权清晰；插件自主性高 | §2.1 |
| 全局 hooks 装一次，所有仓库默认增强 | 目录收窄用插件 projects 作用域；只排除个别仓库用 uninstall | §1.2 |
| 事件订阅只在命令路径生效 | hook 路径订阅会拖慢提交 | 详细设计 §8.2 |
| 用户自己 `npm i` 装插件 | Core 不做安装器；简化 core 复杂度 | 详细设计 §9.3 |
| 默认 mock server | 默认不联网，必须显式关掉才连真服务 | 详细设计 §2.2⑨ |

## 7. 边界与待决议

### 7.1 已拍板的边界

- 插件之间不互相调用（铁律）
- Core 不替插件写文件/落事件（铁律）
- 事件订阅只在命令路径生效
- 全局 hooks 装一次，所有仓库默认增强（`fxdevkit uninstall` 可单独停用某仓库）
- 用户自己 `npm i` 装插件

### 7.2 仍待讨论

| 待决项 | 关键问题 |
|---|---|
| `subscriptions` 是否会松化"插件互相隔离"铁律？ | 订阅是经 Core 事件总线的"间接通道"，跟直接 import 是不是一回事？ |
| 是否需要 `requires` 字段声明插件依赖？ | 强声明 vs 弱约定？ |
| 第二个插件的形态 | 哪种能力最有说服力证明架构？ |
| 远程仓库名 `FocusDevKit` 与产品名 `fxDevKit` 不一致 | 该改哪个？ |
