## 二、协作约定

这个项目的协作方式约定。对贡献者同样适用——尤其是「先判断再动手」和「不许用自建框架冒充事实」这两条。

- **先判断，再动手。** 提出一个改法时，先评估它是否合理，主动指出隐患、代价或更优做法，而不是机械执行后再合理化。
- **对齐优先，动手其次。** 默认停在「复述理解 + 列方案 + 列改动面 + 等确认」；只有明确说「动手 / 去做」才改代码。
- **区分「立场表达」与「行动指令」。** 「这是垃圾设计」「我肯定不会用」「可以砍掉」这类话往往是认知决策，未必是开工令。
- **不许用自建框架冒充事实。** 缺少事实时，不得临时搭一个分类框架（分层、矩阵、四象限）配图呈现，让它看起来像行业共识。推测必须显式标注为推测，不确定必须说不确定。
- **说「专注 X」就只谈 X。** 不用「先对齐方法」把话题拉回流程层，不顺带提别的事。
- **「看这个路径是否可行」是求评估，不是开工令。** 给完判断把控制权交回，等下一步指令。
- **技术解释必须直白具体。** 抽象概念（契约、门面、投影、编排）首次出现时必须立刻用具体代码位置、终端输出、使用场景落地。
- **文档分四层**：门面层（README）/ 概念层（架构设计、概念词典）/ 实现层（详细设计、修改指南）/ 战略层（产品定义）。同一句话放错层就是噪音。门面层不写战略。
- **承诺式的进度报告是反模式。** 一轮只交付「对齐结论」或「动手结果」中的一种，不是两者。
- **中文优先**：沟通与文档命名都用中文（如 `readme_zh_cn.md` 这类中文语义文件名）。
- **文档没有最终版**，随产品迭代持续更新，README 也一样，不是一次性定稿。文案风格偏克制、正式，避免口语化。
- **架构讨论顺序固定**：先整体设计 → 再内核（core）设计 → 插件单独讨论。插件是独立个体，内核不关心也不得讨论插件内部实现细节，只对契约负责。

## 三、已定型的决策

### 3.1 产品定位（2026-09-09 定案，覆盖此前所有表述）

- **fxDevKit 是对人的增强**：人有目标，需要能力去达成，**能力就是插件**，需要什么装什么。不是「研发工具」，不是「插件宿主」。
- **三种入口**：自动触发（动作发生即执行）/ 主动触发（敲命令）/ 对话触发（AI 调 skill + MCP，演进方向）。三者是并列的一等入口，通向同一个调度内核。
- **研发只是当下目标**（因为使用者是研发）。换目标 = 换插件，内核一行不动。内核不含领域语义是这一点的前提（现状 git 语义偏重是已知债，**不再新增**）。
- **契约位置已预留但未实现**：skill / AI 大脑 / MCP / IM 入口。别提前做。

### 3.2 架构与两条铁律（2026-09-04 拍板，2026-09-09 修正）

- **四层**：`cli 命令层` → `core 内核` → `plugin-* 插件`。单向依赖，插件只依赖 sdk。
- **铁律 1**：插件之间**不允许互相调用**，内核不提供任何插件间通道。
- **铁律 2（09-09 修正）**：原表述是「插件只能用内核通用模块」，改为「**通用下沉内核、专属留在插件**」。通用边界靠审核识别（复用度 / 副作用面 / 独立性），不靠预判。
- **core 内部两块**：调度器（发现 / 装载 / 派发 / 兜底）+ 通用模块（git、config、logger、events、server、paths、hooks）。
- **插件手动安装**：用户自己 `npm i -D` / `npm i -g`，内核只负责发现。不做安装器、启停状态机、来源记录、命令注册表。
- **按需解析**：调度时发现插件缺失 → **只提示放行，不在 hook 路径内自动安装**；补齐走显式命令。
- **严格识别三层**：身份识别（清单 id 与代码声明一致）、能力识别（按 permissions 授予，未声明给空实现而非报错）、边界识别（只注入插件自身数据）。

### 3.3 配置模型（2026-09-09 拍板，XDG-style）

- **本质是 XDG Base Directory Spec**：用户配置永远跟人走（`~/.fxdevkit/`），不跟安装走。这是 npm/git/yarn/codex 的行业惯例，不是个人偏好。
- **两层是「源码默认 + 用户覆盖」**，服务的对象不同，所以没有谁覆盖谁的优先级：源码默认在 npm 安装目录（不可改、升级会被覆盖）；用户覆盖在 `~/.fxdevkit/config.yaml`（跟人走、跨升级保留）。
- **绝不要把 npm 源文件当配置界面**——架构原则，不是可选项。
- **工程目录零侵入**：`<repo>/.fxdevkit.yaml` 这一层**已砍掉**（YAGNI）。装完直接用，无需碰任何仓库。
- **范围控制（09-14）**：机器级装一次，所有目录默认增强；排除走 `exclude` 黑名单。原先写在 `.git/config` 的 `fxdevkit.enabled` **已废弃**——不入版本控制，重新 clone / 换机器即丢。
- **加载顺序（低→高）**：插件源码默认 → 用户配置 → env / CLI flag。
- `deepMerge`（`packages/core/src/config.ts`）对数组是**整体替换**，不是逐条合并。用户写 `rules` 必须把全部规则写全。

### 3.4 CLI 命令约定

- **CLI 不硬编码任何插件 id**，插件命令走 `fxdevkit <插件 name> <cmd>` 路由（按 name 匹配，非 id）。
- **不按研发阶段分组**（曾提过 `commit/api/test/release`，被否决）。当前命令：`-v` / `-h` / `status` / `doctor` / `install` / `uninstall` / `disable` / `enable` / `update` / `plugin` / `config` / `report` / `trace` / `logs` / `hook`（内部）。
- **一动词一对象原则（09-14）**：`install` / `uninstall` 只管机器级（挂载 / 卸载全局 hooks，不存在 `--global` 修饰）；`disable` / `enable` 只管目录级（写 / 移 `exclude`）。动词与对象一一对应，不用同一个动词靠参数分流。
- **`-v` = version**（不与业界 verbose 惯例妥协）。将来加 verbose 只能用 `--verbose`。
- **命名原则（09-08）**：裸命令操作主服务；`plugin` 前缀保留表明作用域；主服务自身操作不加 self 前缀。
- **插件 id 规则（09-14）**：必须形如 `plugin-xxx`（小写字母 / 数字 / 连字符），内核在发现阶段校验，不合规的标记跳过（原因见 `plugin list` / `doctor`）。
- **形态参照 lark-cli**（全局安装 + 用户目录核心配置 + doctor），但不照搬其领域分组。

### 3.5 可观测性（2026-09-18）

- 内核自身事件一律 `plugin = 'core'`（`core/src/trace.ts` 的 `CORE`），与插件事件分开。
- **「增强生效」只有一种判定**：插件 hook 跑完落 `hook.handled`；被调用但被任何一关拦下落 `hook.skipped { hook, pluginId?, reason }`。不做这个区分，回溯就会给出「昨天还在生效」的假象。
- 状态变更也落事件：`hooks.installed` / `hooks.uninstalled` / `scope.enabled` / `scope.disabled`。
- 回溯入口 `fxdevkit trace`；`fxdevkit report` 顶部带「最近一次增强」概览。二者同源事件流。
- **不许用事件 / 日志的空白反推历史**：记录系统上线之前的时段是物理黑洞，只能说「自 X 日起无记录」，不能说「从来没生效过」。
- 事件落盘受 `telemetry.enabled` 控制，关掉遥测后回溯不再有数据。

### 3.6 自定义规则归属（2026-09-21 拍板，2026-09-25 修订默认规则）

- **规则是插件私有概念，不做插件层通用能力。** 结论：规则是给插件自己用的，不该上升到插件层做通用抽象。
- `rules` 机制只在 `plugins/commit-rules/src/index.ts` 内实现：四种 action（`skip` / `prefix` / `suffix` / `template`）+ pattern 短路匹配 + 兜底规则 + `assertIdempotent` 幂等交叉校验 + `check` 命令供 CI 复用。sdk 只提供 `defaultConfig` + `validateConfig?`，**内核不认识「规则」**。
- **换前缀有三个连带动作，缺一不可**（已实测）：① 改兜底规则的 `value` ② 同步改它的 guard skip 规则（否则 `assertIdempotent` 直接抛错）③ 留 legacy skip 规则，否则历史提交在 CI `check` 里会判不合规。
- 新增插件命令必须同时加到 `plugins/commit-rules/package.json` 的 `fxdevkit.commands` 数组，否则 CLI 不路由。

**默认规则的判据（2026-09-25 修订，推翻旧默认值）**

判据是「这次提交在 git 历史图里是不是一个**工作单元**」，不是「message 是谁写的」，也不是「改动是不是代码」：

| commit | parent 数 | 角色 | 打标 |
|---|---|---|---|
| 普通提交 | 1 | 工作单元 | ✅ |
| `git revert` | 1 | 工作单元：有自己的 tree 和 diff，是真实的状态变更 | ✅ |
| `git merge`（--no-ff） | 2 | 拓扑节点：连接两条分支，不代表新工作 | ❌ |
| `git cherry-pick` | 1 | 已有工作的搬运，原提交已打过标 | ❌（流程守卫拦） |
| `git commit --amend` | 1 | 重写上一个节点 | ❌（流程守卫拦） |

因此默认规则从「`ai-explicit` + `no-ai` + `default`」改为「`default-guard` + `git-merge` + `default`」：

- **删掉 `no-ai`**（原 `^(chore|docs|merge|revert)[:\s]`）。两个理由：① 文档是资产，前缀标记的是「这次提交发生在 AI 增强环境下」而不是「这次改动是不是代码」；② 一次提交常同时含代码和文档，Conventional Commits 的 type 由人主观挑，拿它推测 AI 参与度不可靠。实测这个 pattern 对 git 自动生成的 message（`Merge branch ...` / `Revert "..."`）**一条都没命中过**（大小写 + 后面跟引号不是冒号），它只拦了手写的 `chore:` / `docs:`。
- **revert 要打标**。它是单 parent、有自己 diff 的工作单元，也是 GitFlow 里最需要追溯的一类操作（为什么回滚）。注意 `git revert` 不在流程守卫里（守卫只认 merge / rebase / cherry-pick / amend），它走规则链。
- **`git-merge` 这条规则是给 CI 用的**：提交时 merge 已被流程守卫的 `isMerge` 拦下，但 `commit check` 校验历史提交时没有 git 上下文，只能看 message，而 git 的 merge message 格式固定。
- 守卫统一命名为 `default-guard`（原来默认配置里叫 `ai-explicit`，与 `prefix` 命令生成的守卫不同名）。代价：**每次换前缀都会生成一条 legacy**（守卫只对应当前兜底值，值一换旧值就没人认）——这是对的，历史提交并存多种前缀，CI 都要放行。

### 3.7 配置写回通道 configStore（2026-09-23 已落地）

- **sdk 只加了一个接口**：`ConfigStore { set(patch) }`，挂在 `CommandContext.configStore`。**hook 路径不给**（hook 必须只读 + 1000ms 硬超时）。
- **内核包命名空间**：`runPluginCommand` 写成 `writeUserConfig({ plugins: { [pluginId]: patch } })`。写成内核代写而不是插件自己写，就是为了让插件**拿不到路径、没法越界**——边界靠结构强制，不靠插件自觉。
- **权限门控**：声明 `fs:global` 则真写，未声明给空实现 + warn（延续「未声明给空实现而非报错」）。
- **已知代价**：`writeUserConfig` 是 `stringifyYaml` 整份重写，**用户 YAML 的注释不保留**（命令里已打 warn）。
- 三个命令的分工：`commit rules` 只读列出生效规则与来源；`commit prefix "<值>"` 原子改兜底前缀，**只覆盖前缀一个维度**，不外扩成正则规则编辑器；`commit check` CI 只读校验。
- 连续换前缀会累积 legacy（旧 guard 降级成 `legacy-N`）——**这是正确行为**，历史提交里并存多种前缀，CI 都要放行，别当冗余清理。

### 3.8 产品方向判断（2026-09-04 的竞品事实）

- **git-ai（usegitai.com）** 已用「行级归因 + Git Notes + agent postToolCall checkpoint」占据 AI 代码归因场景，2026-06 达 2049 stars，支持 10+ agent，并明确评价「commit message 级归因太钝」。

- **插件化架构需要 ≥2 个插件才能自证**；单插件时架构是净开销。
- **半年验收门槛**：内核现在 1931 行，若涨到 3000 行而能力仍只有 2 个，算架构失败。

## 五、待办与已知缺口

### 5.1 已知缺口

| 缺口 | 说明 | 状态 |
|---|---|---|
| **`prefix` 修不了坏配置** | `runPluginCommand` 在 `validateConfig` 抛错时直接 `return 1`，命令 handler 没机会跑。手写一份漏 guard 的 rules 后，`commit prefix` 和 `commit rules` 都被同一句「配置非法」挡回——而「改 YAML 改坏了 → 用命令修回来」正是它最该覆盖的场景。候选修法：`CommandSpec` 加可选 `onInvalidConfig: 'run' \| 'fail'`（默认 fail），内核约 3 行，只给 `prefix` / `rules` 标 run，`check` 维持严格 | 未修，待确认 |
| **feishu 测试 flaky** | 「系统指令文件写失败要返回空串」用 `D:\nul\not-a-real-dir\x.md` 当「应该写失败」的路径，但 Windows 上 `D:\nul` 能被真实创建，于是首次绿、之后恒红。修法：父路径换成一个已存在的**文件**（mkdir 会 ENOTDIR），别用 `nul` 保留名 | 未修，与主线改动无关 |
| **产品定义文档过时** | `docs/00-产品定义.md` 里「自动 / 主动 / 对话触发方式」的旧分类与示例命令（`fxdevkit commit-msg gen`）是 09-18 之前的表述，已被 §3.1 覆盖，但文件本身没改 | 未动，战略层文档改法待定 |
