# fxDevKit 修改指南

> 想动代码时从这里开始。5 个典型场景，每个都列「改什么 / 怎么改 / 怎么验证 / 风险」。
>
> 阅读路径：按场景对号入座，不用通读。

---

## §0. 修改前必看

**改动前先确认两件事**：

1. **跑一遍 `fxdevkit doctor`** —— 当前是健康的吗？后面你才能判断改动有没有把系统搞坏。
2. **明确改动属于哪一层**：

| 你想做的事 | 属于哪一层 | 风险等级 |
|---|---|---|
| 加一个独立插件 | Plugin 层 | 🟢 低 |
| 加一个 CLI 子命令（不调插件） | CLI 层 | 🟢 低 |
| 改 hooks 的执行顺序 / 过滤规则 | Core 调度器 | 🔴 高 |
| 改 ctx 的字段 / 权限模型 | SDK 层 | 🔴 高 |
| 改通用模块的实现细节 | Core 通用模块 | 🟡 中 |
| 改配置合并规则 / scope 判定 | Core 通用模块 | 🟡 中 |

🔴 高风险的改动**改完必须跑端到端验证**（不仅 `doctor`，还要真触发一次 git commit）。

## §1. 加一个新插件（最常做）

### 1.1 场景描述

你想加一个新的能力，例如「自动同步接口变更到 API 文档」、「commit 时跑 lint」。

### 1.2 步骤

**第一步：建目录与骨架**

```bash
mkdir -p plugins/plugin-<name>
cd packages/plugin-<name
```

**第二步：写 package.json**

```jsonc
{
  "name": "@fxdevkit/plugin-<name>",
  "version": "1.0.0",
  "type": "module",
  "main": "dist/index.js",
  "files": ["dist"],
  "scripts": {
    "build": "tsc -p tsconfig.json"
  },
  "dependencies": {
    "@fxdevkit/sdk": "*"          // ← 唯一依赖
  },
  "fxdevkit": {                   // ← manifest（内核读它判断）
    "id": "<id>",
    "name": "<short-name>",       // 命令行短名
    "apiVersion": 1,
    "hooks": ["commit-msg"],      // 或 "commands": ["check"]
    "permissions": ["fs:repo"]    // 按需声明
  }
}
```

> 新增一个插件命令必须**同时**加进这里的 `commands` 数组，否则 CLI 不路由到它（`runPluginCli` 先比对数组，再调 handler）。
> 想让插件把自己的配置写回 `~/.fxdevkit/config.yaml`，需要声明 `fs:global`（`ctx.configStore` 据此授予）。

> 字段详解见 [`概念词典.md §1.2`](概念词典.md#12-清单manifest)

**第三步：写源码**

```ts
// plugins/plugin-<name>/src/index.ts
import { definePlugin } from '@fxdevkit/sdk'

interface Config {
  greeting: string
}

export default definePlugin<Config>({
  id: '<id>',                              // ← 必须和 manifest.id 一致
  defaultConfig: { greeting: 'AI ' },
  validateConfig(raw) {                   // 可选：归一化 + 校验
    const r = raw as Partial<Config>
    return { greeting: typeof r.greeting === 'string' ? r.greeting : 'AI ' }
  },
  hooks: {
    'commit-msg': async (ctx) => {
      const fs = await import('node:fs')
      const file = ctx.messageFile
      if (!file) return 'accept'
      const msg = fs.readFileSync(file, 'utf8')
      if (!msg.startsWith(ctx.config.greeting)) {
        fs.writeFileSync(file, ctx.config.greeting + msg)
      }
      return 'modify'
    },
  },
})
```

**第四步：加 tsconfig.json**（参考 `plugins/commit-rules/tsconfig.json`）

**第五步：编译 + 全局 link**

```bash
# 在仓库根目录
npm install                                # 让 workspaces 识别新包
npm run build -w @fxdevkit/plugin-<name>   # 编译
cd plugins/plugin-<name>
npm link                                   # 全局生效（同机）
```

**第六步：写文档**（两处，保持索引同步）

1. 在插件包下写 `plugins/plugin-<name>/README.md`（工作原理、配置、使用，参考 `plugins/commit-rules/README.md`）
2. 在 [`docs/插件列表.md`](插件列表.md) 加一行索引

### 1.3 验证

```bash
# 1. 插件被发现
fxdevkit plugin list
# 应看到新插件，且 status=ok

# 2. 端到端：真触发一次 hook
cd /d/some/git-repo
echo "test: hello" > /tmp/msg.txt
fxdevkit hook commit-msg /tmp/msg.txt
cat /tmp/msg.txt                             # 应看到 AI test: hello

# 3. 看日志
fxdevkit logs --last 10
```

### 1.4 风险

🟢 **低**。插件之间互相隔离，错了不影响别的插件。但要注意：
- `id` 必须与 manifest 一致（`loadPlugin` 会拒绝装载）
- `apiVersion: 1` 必须匹配内核 `PLUGIN_API_VERSION`

## §2. 改 dispatch 调度逻辑

### 2.1 场景描述

你想改 hooks 的调度流程，例如：
- 改 timeout（现在 1000ms）
- 改 hook 的过滤规则
- 改 reject 的传播逻辑（现在是「任一 reject = 阻断」）
- 加新 hook 阶段（例如「先跑 security 扫描再跑 lint」）

### 2.2 步骤

**第一步：定位代码**

所有调度逻辑集中在两个函数：
- `dispatchHook(hookName, args)`：hook 路径入口 —— `packages/core/src/kernel.ts`
- `runPluginCommand(pluginId, command, args)`：命令路径入口 —— 同上

**第二步：典型改动示例**

| 改动 | 在哪改 | 代码示例 |
|---|---|---|
| 改 timeout | `kernel.ts` 的 `dispatchHook` 内 | `const timeoutMs = config.hooks?.timeoutMs ?? 1000` |
| 改 reject 传播 | `kernel.ts` 的结果收集 | `let rejected = false; if (result === 'reject') rejected = true;` |
| 改候选插件过滤 | `kernel.ts` 的 `selectPlugins` 调用 | 在 `selectPlugins(discoverPlugins(...), hookName)` 前后加逻辑 |
| 加新调度阶段 | 在 `dispatchHook` 内插一行 | 例如 `await preDispatchHook(ctx)` |

### 2.3 验证（端到端，必须）

```bash
# 1. 编译
npm run build -w @fxdevkit/core

# 2. health check
fxdevkit doctor

# 3. 真触发一次 hook
cd /d/some/git-repo
echo "test: hello" > /tmp/msg.txt
fxdevkit hook commit-msg /tmp/msg.txt

# 4. 看日志（确认调度阶段都对）
fxdevkit logs --core --last 10

# 5. 测异常路径（让某个插件 reject，确认阻断）
echo "intentional bad" > /tmp/bad.txt
fxdevkit hook commit-msg /tmp/bad.txt
echo "exit code 应为 1"
```

### 2.4 风险

🔴 **高**。调度器是系统核心，改坏了可能：
- 所有 hook 都不再被增强
- 所有 commit 都被阻断（即使是好的 commit）
- 所有插件抛错导致 git 卡住

**改完必须做两件事**：
1. 真跑一次 git commit，确认正常路径没问题
2. 真跑一次会触发 reject 的 commit，确认阻断路径没问题

## §3. 改 SDK 契约

### 3.1 场景描述

你想改 ctx 的字段、新增 permission 类型、或新增 hook name。
**注意**：SDK 是契约层，**改了会影响所有插件**。

### 3.2 步骤

**第一步：定位**

`packages/sdk/src/index.ts` 集中了所有 SDK 类型：
- `HookName` 类型（行 11-17）
- `Permission` 类型（行 19-26）
- `PluginManifest`（行 28-41）
- `HookContext` / `CommandContext`（行 74-98）
- `PluginDefinition`（行 132-145）

**第二步：典型改动**

| 改动 | 在哪改 |
|---|---|
| 加新 hook 名（如 `post-commit`） | `HookName` 类型加一项；同时 `packages/core/src/hooks.ts` 的 `MANAGED_HOOKS` 加上 |
| 加新 permission（如 `net:browser`） | `Permission` 类型加一项；同时 `kernel.ts` 的 ctx 构造里加对应分支 |
| 加 ctx 字段 | `HookContext` 加字段；同时 `kernel.ts` 构造处注入 |
| 加新 API（如 `subscriptions`） | `PluginDefinition` 加字段 |

### 3.3 验证

```bash
# 1. 编译所有包（SDK 是基础）
npm run build

# 2. 所有插件必须跟着编译成功
npm run build -w @fxdevkit/plugin-commit-rules

# 3. 跑端到端
fxdevkit doctor
cd /d/some/git-repo && git commit -m "test: sdk change"
fxdevkit logs --last 10
```

### 3.4 风险

🔴 **高**。SDK 改动会破坏插件编译。最安全的做法：
- **加字段**而不是改字段（向后兼容）
- 加新值时给默认值（不强制插件改 manifest）

## §4. 排查问题

### 4.1 排查路径（按顺序）

```
问题？ → fxdevkit doctor                          # 健康总览
      → fxdevkit logs --core --last 50            # 内核调度日志
      → fxdevkit logs --plugin <id> --last 20     # 某插件的日志
      → fxdevkit status                           # 当前仓库状态
      → cat ~/.fxdevkit/logs/2026-09-08.log       # 直接看文件
      → fxdevkit config validate                  # 配置是否合法
```

### 4.2 常见问题速查

| 症状 | 大概率原因 | 看哪 |
|---|---|---|
| `doctor` 报 hooks 未安装 | 没跑 `fxdevkit install` | `git config --global core.hooksPath` |
| `doctor` 报「入口无效」 | CLI dist 没编译或被移动 | `ls packages/cli/dist/index.js` |
| `doctor` 报插件未加载 | manifest 错 / id 不一致 / apiVersion 不匹配 | `fxdevkit plugin list` |
| commit 没加 `AI ` 前缀 | 当前目录被 `disable` 排除 / 全局 hooks 没装 / 插件有 bug | `fxdevkit status` + `fxdevkit logs --core` |
| Cursor GUI 提交不生效 | Cursor 屏蔽了 core.hooksPath（已知 bug） | 见命令手册 FAQ |
| 插件抛错 | handler 代码 bug | `fxdevkit logs --plugin <id>` |
| 配置不生效 | 改了 `config.yaml` 但没跑新命令 | 配置是「下次运行时」生效，不是热加载 |
| `fxdevkit logs` 没东西 | `FXDEVKIT_LOG=0` 关了落盘 / 当前日志级别阈值高于事件级别 | `fxdevkit logs --level debug` |
| git 命令在 Cursor 里启动失败 | wrapper 找不到 / 起不了 git | `~/.fxdevkit/logs/wrapper.log`（只记异常；要转发细节先建 `~/.fxdevkit/wrapper-debug`） |
| `fxdevkit logs --days` 出现奇怪的「日期」 | 只看 `YYYY-MM-DD.log`，`wrapper.log` 不算一天 | `fxdevkit logs --days` |

### 4.3 加调试日志

```bash
# 让所有 info 也实时打到 stderr（默认只落盘）
FXDEVKIT_DEBUG=1 fxdevkit status

# 临时改日志级别阈值
FXDEVKIT_LOG_LEVEL=debug fxdevkit hook commit-msg /tmp/msg.txt

# 关掉落盘（保留 stderr）
FXDEVKIT_LOG=0 fxdevkit status
```

## §5. 加一个新 CLI 命令

### 5.1 场景描述

你想加 fxdevkit 的内置子命令，例如 `fxdevkit cache clean`、`fxdevkit doctor`。

### 5.2 步骤

**第一步：定位**

`packages/cli/src/index.ts` 的 `main()` 函数是所有命令的入口，约 712-775 行。
命令分支是 `switch (command)`，加新分支就在这里加 `case`。

**第二步：典型改动**

```ts
// 在 main() 的 switch 里加：
case 'cache': {
  const [action, ...args] = rest
  if (action === 'clean') return cmdCacheClean()
  process.stderr.write(`[fxdevkit] 未知 cache 动作：${action}\n`)
  return 1
}

// 在文件其他位置加：
function cmdCacheClean(): number {
  // 你的实现
  return 0
}
```

**第三步：更新 help**

`renderHelp()` 函数（同文件）也需要加新命令的说明。

**第四步：更新文档**

`docs/命令手册.md` 加新命令说明。

### 5.3 验证

```bash
# 1. 编译
npm run build -w @fxdevkit/cli

# 2. help 应显示新命令
fxdevkit help

# 3. 真跑一次
fxdevkit cache clean

# 4. exit code 应为 0
echo $?
```

### 5.4 风险

🟢 **低**。CLI 是最外层，加新命令不动核心。但：
- 不要硬编码任何插件 id（命令手册的「CLI 不硬编码任何插件 id」是铁律）
- help 必须同步更新（不然用户不知道有这个命令）

## §6. 改通用模块（实现细节）

### 6.1 场景描述

你想改 `logger.ts` 的输出格式、`events.ts` 的落盘字段、`server.ts` 的 mock 行为等。
**不动接口**，只改实现细节。

### 6.2 步骤

**第一步：定位模块**

| 模块 | 文件 | 改什么 |
|---|---|---|
| 路径约定 | `packages/core/src/paths.ts` | `paths` 对象的字段 |
| git 信息采集 | `packages/core/src/git.ts` | `detectGitContext` 的实现 |
| 配置加载 | `packages/core/src/config.ts` | `loadConfig` 的合并规则 |
| 事件 | `packages/core/src/events.ts` | 落盘格式、订阅分发逻辑 |
| 日志 | `packages/core/src/logger.ts` | 输出格式、落盘路径、打印策略 |
| 作用域 | `packages/core/src/scope.ts` | `isPluginInScope` 的匹配规则 |
| hooks 安装 | `packages/core/src/hooks.ts` | dispatcher 脚本内容、安装策略 |
| server | `packages/core/src/server.ts` | mock / 真实 / 拒绝 三态实现 |

**第二步：改 + 验证**

每个模块的验证方式：

| 模块 | 验证 |
|---|---|
| paths | `fxdevkit status` 看是否报错 |
| git | `fxdevkit status` 看 git 信息是否正确 |
| config | `fxdevkit config show` 看合并后的配置 |
| events | `fxdevkit hook commit-msg /tmp/msg.txt && cat ~/.fxdevkit/events/*.jsonl` |
| logger | `fxdevkit logs --last 5` 看格式对不对 |
| scope | 改 `~/.fxdevkit/config.yaml` 的 `projects`，看 `fxdevkit status` 是否命中 |
| hooks | `fxdevkit install && git commit -m "test"` |
| server | 看 `fxdevkit doctor` 的 server 状态行 |

### 6.3 风险

🟡 **中**。实现细节改错会导致数据格式、行为偏差，但**接口不变所以不影响插件**。
改完需要跑端到端验证。

## §7. 改后端到端验证 checklist

无论改了哪层，跑这个 checklist：

```bash
# 1. 编译所有包
npm run build

# 2. health check
fxdevkit doctor

# 3. 真触发一次 hook
cd /d/some/git-repo
echo "test: end-to-end check" > /tmp/msg.txt
fxdevkit hook commit-msg /tmp/msg.txt
echo "exit=$?"                    # 应为 0

# 4. 看日志
fxdevkit logs --core --last 10

# 5. 跑 reject 路径（如果有 reject 规则）
echo "intentional bad" > /tmp/bad.txt
fxdevkit hook commit-msg /tmp/bad.txt
echo "exit=$?"                    # 应为 1（被 reject 阻断）
```

如果某一步不符合预期，看日志里的「[id] 完成：xxx」行：
- `accept`：插件正常放行
- `modify`：插件改了文件
- `reject`：插件拒绝
- 没出现：插件根本没被调起来（说明发现/装载阶段出问题）

## §8. 常见「不该改」的地方

为了避免改坏，以下文件**改之前必须先想清楚为什么**：

| 文件 | 危险点 |
|---|---|
| `packages/core/src/index.ts` | 是 core 的对外导出，改名 = 破坏所有调用方 |
| `packages/sdk/src/index.ts` 的 `definePlugin` | 是 SDK 的入口，改签名 = 所有插件编译失败 |
| `packages/core/src/plugins.ts` 的 `discoverPlugins` | 改扫描目录会让插件突然消失 |
| `packages/core/src/hooks.ts` 的 dispatcher 脚本模板 | 改坏会让所有 git hooks 都跑不起来 |

**改之前问自己**：用户感知是什么？这个改动的回滚成本是多少？
